---
title: فحوص السلامة
description: نقطة النهاية التي تُخبر أدوات التنسيق وموازنات التحميل وأدوات مراقبة التشغيل ما إذا كان Mitra يعمل، وفحص السلامة في Docker المبني عليها.
---

يجيب Mitra عن سؤال واحد لكل ما يراقبه: هل هذه النسخة تعمل؟ اسأله على هذا العنوان، الذي لا يحتاج إلى تسجيل دخول:

```text
GET /api/health
```

يفحص Mitra الشيء الوحيد الذي لا يستطيع العمل دونه، وهو قاعدة بياناته:

| الاستجابة | المعنى |
| --- | --- |
| `200` `{"status":"ok"}` | يعمل. قاعدة البيانات تستجيب. |
| `503` `{"status":"error"}` | لا يعمل. لم تستجب قاعدة البيانات، أو استغرقت وقتًا طويلًا. |

الإجابة مقتضبة عمدًا. فهي لا تحمل أي تفاصيل عن الإصدار أو البناء قد تكشف لغريب ما تشغّله، ولا تُخزَّن مؤقتًا أبدًا، فيرى كل فحص الحالة الحالية.

الخدمات المربوطة، مثل خادم CalDAV أو Notion أو Google أو مزوّد تسجيل الدخول أو خدمة الترميز الجغرافي، ليست جزءًا من الفحص. فانقطاع قصير في إحداها لا ينبغي أن يجعل Mitra نفسه يبدو معطلًا.

## Docker

تتضمن الصورة بالفعل فحص سلامة لـ Docker يستخدم نقطة النهاية هذه، لذا يعرض `docker ps` و`docker inspect` حالة Mitra الفعلية دون أي إعداد. تُظهر الحاوية الجديدة `starting`، ثم `healthy` بمجرد أن تعمل قاعدة البيانات. ويتبع الفحص [`MITRA_PORT`](configuration.md) إن غيّرته.

```bash
curl -f http://localhost:3000/api/health   # fails unless Mitra is healthy
docker inspect --format '{{.State.Health.Status}}' mitra
```

## Kubernetes

وجّه فحص الحيوية وفحص الجاهزية كليهما إلى نقطة النهاية:

```yaml
livenessProbe:
  httpGet:
    path: /api/health
    port: 3000
  periodSeconds: 30
readinessProbe:
  httpGet:
    path: /api/health
    port: 3000
  periodSeconds: 10
```

## أدوات مراقبة التشغيل

يمكن لأي أداة مراقبة عبر HTTP، مثل Uptime Kuma أو Healthchecks.io أو الفحص المدمج في موازن التحميل، أن تستطلع `/api/health` وتعدّ أي استجابة غير `200` توقفًا عن العمل. ويعمل ذلك بالطريقة نفسها مع [تسجيل الدخول](sso.md) ودونه.

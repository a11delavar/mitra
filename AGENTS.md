# AI Agent Instructions

## Frontend
- **Stack**: TypeScript, Lit, modern CSS, standard web components. Decorators (`@component`, `@property`, `@state`); styles in `static override get styles()`.
- **Light DOM for features** (`createRenderRoot() { return this }`), for global theming and view transitions; register every light-DOM component's `styles` in `Mitra.ts`. Design controls are shadow DOM (§Design Library).
- **CSS**:
  - Nest every rule along the DOM; state is a boolean data attribute nested under its element (`.child { &[data-state] {} }`), never fought with `:host([attr])`.
  - Domain class names (`.header`, `.time`), never structural (`wrapper`, `btn`); flat templates.
  - Logical properties only; no `box-shadow` for one-sided borders (use pseudo-elements).
  - `rem` for layout; `px` only for 1px borders and container query thresholds. Container queries, not media queries.
  - No fallbacks in `var(--theme-var)`. Grid/Flexbox over JS math.
  - `all: unset` overrides `[hidden]`: restate `&[hidden] { display: none }`.
- **Dates**:
  - Frontend: `@3mo/date-time`'s global `DateTime` for formatting and view math (`.equals()`, `.dayStart`, `.format()`), no raw `valueOf()` math. Shared and backend: Temporal (polyfilled by `scripts/injectTemporalPolyfill.ts`).
  - Days and instants meet on `TimeZone`: `zone.dayOf(instant)` is the day it falls on there, `zone.midnightOf(day)` the instant that day begins, `zone.shift(instant, from, to)` moves an instant by a wall-clock distance (`TimeZone.UTC`, `TimeZone.device`, and `TimeZone.default` where none is known, as on the server, where `TimeZone.local` is none).
  - **An all-day entry's dates are days**, kept as UTC midnights in the database, on the wire and on the server. The browser's `Entry` holds each as the midnight that begins it there, a plain field: each date is declared `@Entry.date()`, whose converter reads `allDay` from the same entry and translates only when crossing the wire (`TimeZone.local`: browser zone, `TimeZone.deviceId`, refreshed only on offset change or page visibility; passthrough on server). Never use getters/setters on dates: views read them thousands of times per frame. Writes with `?tz=` are rejected (409); all-day dates travel as UTC midnights and convert to `TimeZone.local` on the client. Day lists (`exdates`) convert alike (`@Entry.days()`), and all-day rules repeat in `TimeZone.local`. `EntryPatch` converts dates identically (`EntryPatch.of` bundles `allDay` with dates).
  - **A floating time is a wall clock** (`EntryTimeZone.floating`), kept as if in UTC in the database, on the wire and on the server. The browser holds it as the instant that wall clock reads in `TimeZone.local`, converted by the same `@Entry.date()` converter, which reads `timeZone` beside `allDay`, so every view places it as any other time; a floating series repeats there, and `EntryPatch.of` brings a floating entry's `timeZone` along with its dates.
  - Never spread a `PlainDate` (its fields are prototype getters).
  - `ICAL.Time` lives only at the .ics boundary (`IcsTime.instantFrom`/`toICALTime`); zoned writes keep the resource's VTIMEZONE.
  - Mitra extends `DateTime` with members named for its domain in `DateTime.<feature>.ts` (module augmentation): facts as getters, formatting as `formatAs…` methods, as 3MO does.
- **i18n**:
  - Natural English keys (`t('Phrase')`); dotted keys only for long prose and palette keyword blobs (`GoToDate.Keywords`). Every dictionary fully translated, keys grouped by feature. Check a key isn't already used in another sense (`t('On')` vs `Toggle.On`).
  - The locale is `Localizer.locales.current`, an `Intl.Locale` (`en` adopts the browser's region, `en-GB`). Hand it whole to Intl formatters and to the device (push sends `String(locale)`; the server's `localizeIn` reads its language). `.language` is the dictionary key.
  - **Language is a locale** (`LocaleSetting`, value `en` or `en-GB`): every language with its regions folded under it, kept on the account (`UserSettings.locale`), so every device follows the one choice (`followAccount`) and agents read it; until one is chosen, the browser's. `AppLocale` writes the one tag (so `-u-` keywords can join later), probes regions via `resolvedOptions().locale`, always offers `001`/`150`/`419` and names them itself (Chromium can't). A region is a format, not a time zone; `mitra-locale-preview` shows what it changes.
  - **Never force a clock**: no `hour12`/`hourCycle`. A time alone is `timeStyle: 'short'`; beside date fields (which `timeStyle` refuses) `hour: 'numeric', minute: '2-digit'`, accepting an unpadded German "1:05". The week axis names whole hours alone on a 12-hour clock ("4 PM", `resolvedOptions().hour12`), else `timeStyle: 'short'` ("16:00"), and a zone column off here by a half hour keeps its minutes ("4:30 PM"); the now label is always `timeStyle: 'short'`.
  - Let the Localizer do grammar: plurals are dictionary arrays, numbers and arrays format themselves, ordinals by `Intl.PluralRules({ type: 'ordinal' })` (`Recurrence.ordinal`). Never interpolate a raw number (`count.format()`, `formatAsPercent()`), never a literal `%` in a key.
  - `i18n/index.ts` re-registers `LocalizerController` on `PageComponent`/`DialogComponent`: lit snapshots initializers at finalize time.
  - Integration `label`s are localized at render; the instance name is `session.instance.displayName` (`MITRA_NAME`, else `t('Mitra')`).
  - Fonts ship from `dist/` (`src/app/fonts.css`: Inter, Vazirmatn by `unicode-range`), never a CDN. Noto Sans SC joins the stack only under `body:lang(zh)`, so Japanese or Korean text elsewhere keeps its own glyphs.
  - Chinese is Simplified (`zh`): dictionaries are keyed by language alone, so the regions Intl writes in Traditional characters (TW, HK, MO) still read their dates that way. `formatToParts` literals can be words (Chinese writes the month's 月 as one): never drop them all.
- **Secrets are withheld by their converter** (`@converter(withheld(...keys))`, `infrastructure/model/withheld.ts`): the server sends them blank and keeps what a request carries; no keys withholds the member itself (`AccessToken.hash`). Never a hand-written `toJSON`.
- **Value objects persist themselves**: a static `Mapper` (MikroORM `Type`) for the database and a static `converter` (`@converter(X.converter)`; an object `{ key: … }` names the wire field) for the API, as `EntryType` and `UserTimeZones` do, never a parallel `Stored…` shape. A nullable column reaches the mapper as `null` in both directions, though the ORM loads an empty column as an absent field (`forceUndefined`): the domain holds no `null`.
- **Domain vs view**: domain records (`Entry`, `Source`, `Integration`) hold no layout math; layout is `EntrySegment`/`EntrySegments` in `entries/client/`.
- **Time grid**: one row per layer, everything on it placed by its minute's fraction of the day (chips and availability absolute in their grid area, `inset-block` from `--_from`/`--_to`; hour lines, axis labels and the now line relative, `top` from `--_at`), never 1440 minute rows: Firefox rounds each track to 1/60 px, and a zoom moved what lay deep in the day in 7–15 px steps. One scroller with sticky headers and axis, no JS scroll sync. Overlaps by interval graph coloring, passed only as `--overlap-slot`/`--overlap-total`. Cross-day entries split at the data layer (`getEntriesForDay`), never one element across midnight (`continuesNext`/`continuedFromPrevious` clamp rows and radii). Each day's `.entries` is `content-visibility: auto` (days out of view skip their chips), a stacking context at `z-index: 2` over the day's own surface, so hour lines and connectors stay between; never on the day itself, whose subgrid it drops (layout 15–30× slower). Variables changed per frame (zoom, lane rows) are registered `inherits: false` on `mitra-days`, and the scroll range is set on the connector layers: an inherited one recalculated every element of the week each frame. The lane height snaps, never transitions. Templates never read layout.
- **Popovers** (`design/Popover.ts`): `mitra-popover` is anchored where there is room, centered otherwise (`--centered`, pure CSS), and with `sheet` a modal bottom sheet below `40rem`; its content is slotted, so switching never rebuilds it. `position-try-order: most-block-size` is forbidden.
  - Entry editor: `mitra-entry-details` (`display: contents`) wraps its `.editor` in `<mitra-popover sheet>`, anchored by `show(segment)`; placement `flip-inline, --centered`, declared in its own stylesheet (`@position-try` names are tree-scoped). A sheet focuses its dialog unless something has `[autofocus]`.
  - Test with CDP touch/mouse events, never `segment.open = true`; the editor is open when `mitra-entry-details:has(> mitra-popover[open])`.
  - **Motion is CSS** (`Popover.ts`): a popover fades and slides from its anchor across the margin gap and leaves the same way, quicker (`overlay`/`display` `allow-discrete`). Each hangs from a **named anchor** declared beside its `position-anchor`: the implicit one from `showPopover({ source })` is dropped mid-exit. Never gate layout other than `display` on `:popover-open`. Whatever removes a popover on close awaits `settle()`. A row appearing in the open editor grows in (`@starting-style`, enabled after opening by a delayed animation and a style query). Dialogs and the palette leave as they came; a `DialogComponent` has no exit yet (@a11d/lit-application removes it synchronously). A tree listbox leaves at once (`transition: none`): Chrome 151 crashes the tab when one fades out of the top layer as another popover opens or its dialog closes.
- **Forms**: seed form-bound fields with `""`, never `undefined`; `merge` uses `||`.
- **Editor rows** (`.field`, `entries/client/editorFields.css.ts`, scoped to `mitra-entry-details`) strip the inner controls' chrome and anchor pickers to the row. Every checkbox is `mitra-checkbox`.
- **Comments**: only non-obvious constraints and platform traps, one or two sentences. Update AGENTS.md with every architectural decision.
- **Docs** (`docs/`, Starlight Markdown, `> [!NOTE]` alerts, relative links): env vars in `configuration.md`, providers in `integrations/<provider>.md`, views in `views/`.

## Design Library (`src/design`)
- Imports nothing from features or infrastructure (`design/boundary.test.ts`), except `Dialog.ts` → `Mitra.styles`. Registered in `design/index.ts`.
- Controls are shadow DOM with `part`s. A control stamps state on its own parts and nests the rules under them; `:host([attr])` only switches the whole host's layout. `:host(:has())` matches nothing in Chromium.
- **Controls**: `Control` delegates focus to its native input and honors `autofocus`; controls re-emit composed `change` (bind with `live()`). `:state(focus-visible)` lets a context ring a control from outside. Event guards use `startedInField`/`startedOnControl`/`startedInOverlay` (`eventOrigin.ts`, `composedPath()`), never `target.closest()`.
- **Selects & comboboxes**: `mitra-select` is a button plus listbox over slotted `mitra-option`s (`::part(listbox)`, reflects `open`). `mitra-combobox` is `floating` or `inline` (Escape fires `dismiss`); `selected` is a value or an array (multiple).
  - `mitra-option-tree` nests options under a `slot="header"` option, chosen like any other; its chevron (`Option.disclosure`) folds the rest, animated natively (`interpolate-size`, `@starting-style`). Folded options are hidden, never disabled (a disabled option is never selected). Values are unique across a list (the controller keys by value).
  - A listbox holding a tree lays rows on shared columns: tick, the component's own (`--mitra-tree-columns`), chevron; groups, trees and rows are subgrids, a component places parts by column (`::part(content) { display: contents }`). Plain selects keep their row layout.
  - The combobox walks trees itself rather than through @3mo/tree's `TreeController`: that popup is fixed at construction and keyed by element, and leaves Left/Right to a text field's caret.
- **Overlays**: a `mitra-popover` subclass declares its `popoverType` (`'manual'` floating, `null` inline), never a blanket `'auto'`. `mitra-popover-container` pairs trigger and popover without IDs, naming the anchor with `!important` (a page rule beats `::slotted`, and a trigger's `all: unset` dropped it). Pickers render on first `beforetoggle` (every editor holds several closed ones).
- **Fields**: segmented `mitra-date-field`/`mitra-time-field`/`mitra-date-time-field` read their `DateTime` in their `timeZone` (the editor passes its lens, the repeat end `UTC`); the date-time field edits a draft (a pick or closing commits, Escape drops). `mitra-date-picker multiple` chooses several days on `@3mo/selectability` (`Toggle`: a press adds or removes, Shift extends a run; its items reach from the months shown to where a run starts, so a run crosses months), its `value` a day or, with `multiple`, the days chosen, as `mitra-combobox`'s `selected`; `isDisabled` names the days that can't be picked, drawn as disabled, keeping its own arrow keys, as `@3mo/navigability` moves in one dimension. `months` shows several in a row (the duplicate dialog asks two), wrapping where narrow, each under its own title with the arrows at the outer ends and its neighbours' days left blank; one cursor moves by date across them, and the months shown move only once it leaves them. `@3mo/segmented-input` gives groups `dir="auto"` and isolates each numeric segment; filled ones rejoin the bidi run (`unicode-bidi: normal`), or an Arabic "3:00 م" swaps hour and minute. `InputField<T>` backs text, search and number fields; `plain` drops the box for a picker's search.
- **Fragments** (`*.css.ts`: `fieldChrome`, `optionRow`, `selected`, `disabled`, `pressable`, `scrollbar`): interpolate with `unsafeCSS`. A context that draws the box itself (the editor's rows) sets `--mitra-field-*`; overlays restore them (`fieldChromeRestored`).
- **Sheets & dialogs**: `mitra-modal-sheet` on 3MO's `SheetController`. Content laid out while closed has zero size (`mitra-tabs` re-reveals on resize). `mitra-dialog` renders in place and announces `pageHeadingChange` only while `boundToWindow`. Two-pane dialogs (Settings, About) use `--mitra-dialog-rail` beside `--mitra-dialog-page`, never a colour of their own.

## Backend & Database (MikroORM, SQLite)
- STI for `Integration` and `Entry` (`discriminatorColumn: 'type'`); a subclass without columns needs no migration, only `ormConfig.ts` and `registerIntegrations.ts`.
- Date columns are `type: 'Date'`, never `'datetime'` (same column): MikroORM compares a `'datetime'` with `equals`, so the Date it loads never matches the milliseconds SQLite keeps, and every flush rewrote every loaded date (`database/dates.test.ts`).
- **Schema**: every boot runs the migrations (`migrator.up()`), dev included; never `orm.schema.update()`, which reads a column replaced as a rename and knows nothing of data. Entity changes need `npm run db:migration:create -- <Name>` (writes the migration, the snapshot and `migrations/index.ts`); `migrations.test.ts` checks the migrated columns match the entities. A migration runs once, in order, on the shape the one before it left, so it never introspects. Use `await this.execute()` where a step reads data. Unlogged legacy databases baseline at current table state: `migrate.ts` replays the chain in memory, logs migrations matching existing columns, and executes remaining migrations on live data.
- **Table rebuilds**: `foreign_keys = off` does nothing inside a transaction, so dropping a parent cascades. Hold children in an FK-free table, drop and recreate, restore children and references (`user.default_source_id`).
- **Children are plain values in the domain** (`@children`, `infrastructure/model/children.ts`): an ORM `Collection` can't change outside a running ORM (the browser, tests), so the decorator hides it (MikroORM's `accessor`) and `owner.<key>` is a plain array, or a collection value object with `as: () => X`. Off the wire unless the member declares a `@converter`. With `saves`, what the parent was set to is saved before every flush (`children.subscriber`), so no write path has to remember a call: a child (an `Entity`) a row `is` equates it, a child whose id another parent's row holds is saved as its `copy()` (an edit of one occurrence carries the recurring entry's), the rest are removed. Where the collection's values are not the rows (`Entry.relations` holds lines, stored as `EntryRelation` rows), `rows` maps what was set to the rows to save; with `unknown`, an owner made outside the ORM and given none reads them as `undefined`. Its queries take `flushMode: COMMIT`, each with a fresh options object (the ORM writes into it). Traps: MikroORM takes a value two fresh instances share by reference as a column default, so `X.of([])` is a fresh object; a subclass entity assigns `init` after `super()`.
- **Included entities** (`@include(() => Source, 'sourceId') source!: Source`, `infrastructure/model/include.ts`): what an id names, read as a member while the id stays what moves it. On the server a read-only relation over the id's column, joined (about 0.03 ms an entry); in the browser found by the id through what `include.from` registered (`Calendars`); an assigned value wins until the id names another, and travels with the id into a clone or copy (`@carried`), so an entry made on the server is told its calendar once (`migrateTo`, or `source` in its init) and reads it in `fit()` and the `status` setter. Never on the wire; the ORM keeps it under an accessor no identifier can spell (`@include source`), as writing through the member saved the target again.
- **An entity's fields declare their role** (`Entity`, `infrastructure/model/Entity.ts`): `@identity()` tells it apart (the row's `id`, or a getter computing one), `@equality()` makes two equal and is all a copy carries, children included (`Integration.sources`); a field with neither is bookkeeping (`uri`, `data`, `rank`, the holder's id). The operations follow and are never written by hand: `is`/`equals` compare, `clone`/`copy` make a new one (a copy runs the constructor, so an id minted there is fresh), `assign`/`equate` make this one the other, by identity or by equality. Copying is deep through the fields of equality: arrays and plain objects are copied, nested entities cloned or copied (a collection of them rebuilt through its `of`), value objects kept by reference. An entity a bookkeeping field points at, the holder a child names, is left out of a clone: whoever takes the child sets it, and MikroORM puts a child into its holder's rows once it names it. The library's `[equals]` is the same one unchanged (`is` and `equals`), so a collection compares its entities by both. A match by something else (a reconcile's `uri`) says so itself. `patch` stays apart: absent keeps, `null` clears. `EntryPatch.fields` declares the wire fields (equality fields plus `relations`).
- **Type conversion** (event ↔ task) re-creates the entry (VEVENT and VTODO can't share a CalDAV resource), compensating on failure; series can't convert (400).
- Discovered sources are saved `enabled: false`. The reconcile (`Integration.getSources`) matches them by address however the provider spells it (`Source.isAt`: `%40` or `@`, a trailing slash), keeps every stored source when a listing names none (Google's hourly tokens make a refused listing read as empty, and a removal takes its entries along), and logs every removal, addition and move. `enabled` is where an entry may live (`Calendars.enabled`); `visible` is a view preference and never removes a destination.
- Local renames survive sync: `Source.remoteName` is the provider's baseline, `name` changes only when the remote one does.
- **Authority**: the backend owns DTSTART, STATUS, TRANSP, SUMMARY, DESCRIPTION, ATTACH; Mitra owns source colors, order, visibility and availability (mirrored upstream as `X-MITRA-*` where possible). The SQLite database is authoritative for users, sessions and local overrides.

## Multi-User & Authentication
- **Modes**: single-user by default (`[default_local_user]`); OIDC with `MITRA_OIDC_ISSUER`, `MITRA_OIDC_CLIENT_ID`, `MITRA_URL` (incomplete config throws). Demo (`MITRA_DEMO=true`, wins over OIDC) opens a `Sandbox` per visitor (`demo-<uuid>` with a `Demo` integration), living `Sandbox.lifetime` (24 h), capped at `MITRA_DEMO_CAP`; dotted paths outside `/api/` never open one; connecting is refused (403).
- OIDC client `identity/server/Oidc.ts` (code + PKCE, `/auth/*`); sessions `Session.ts` (hashed 256-bit cookie, sliding 30 days, `SameSite=Lax`, keeps `id_token` for logout). Unauthenticated `/api/*` is 401, pages redirect to login.
- `Identity` is embedded in `User` (`oidc_*`, unique issuer + subject); `User.provision` creates on first login.
- **Tenant isolation**: query through the `User` (`user.getSources`, `user.filterEntries`, `user.getRelationGraph`, `user.getDevices`, `user.getAccessTokens`), never bare `em.find*` over an id list: `user.filterEntries(em, { range, search, where, sources, limit })` joins through the calendar's integration to the user, reads each recurring entry's overrides and attaches relations. A foreign id is `NotFoundError` (404). `EntryRelation` has no user column, so `targetUid` matches stay in the user's sources. A push endpoint taken over by another user loses its name.
- Errors: `app/server.ts` maps `NotFoundError` to 404 and keeps 4xx/5xx `status`, else 500; an `AggregateError` answers with its first error's status and message, listing all in `errors`.
- **Validation** (`infrastructure/validation/validation.ts`): `@validation(zodSchema)` declares what a member holds once built, judged after construction (`validation.errorsIn`), each failure a `ValidationError` naming its `fields` (400 by `static status`). A converter that changes a type names the form it reads (`schema`, merged into `@a11d/converter`'s `Converter`) and refuses what it cannot read, never turning it into nothing; `validation.schemaOf(Class)` is how a class is written, `validation.read` checks values against it. Converters used once are inlined. Value objects name their own members (`z.enum(EntryOccurrenceChangeScope)`), never restated. A `Validatable<Context>` yields its errors (`*validate`), the caller throws them as one `AggregateError`. `EntryPatch.validate({ entry, from, to, scope })` judges the edit, `Entry.validate()` whether its calendar can hold it, `EntryRelations.validate({ entry, graph })` whether the entry may hold its candidate relations, on `user.getRelationGraph(em, change.related)`, which reaches the entry and their targets; routes ask them once, in one `AggregateError`.
- SSE, push and reminders are per user. SSE scope `'entries'` (default) or `'sources'` (refetches integrations); entry mutations use `'entries'` so `Source` instances survive.

## The Sample Calendar (`integrations/demo/Demo.ts`)
- One fixture serves dev, every demo sandbox and every screenshot, so keep it calm: one entry per concept, the all-day lane empty around today, days within 07:00–19:00, recurring entries on weekday rules or fixed dates, dependency links in `today−2…today+4` clear of chips. Its entries carry the account's home zone (the server's until the first device settles one, since a sandbox opens on the document request, where no zone travels), which their hours and today are read in: `today` is a `DateTime` built in that zone, and every date derived from it keeps it. A rule without a zone repeats at fixed instants. The morning meds alone have none (`EntryTimeZone.floating`, 7:30 wherever their taker is), showing "Same time everywhere".
- `credentials.seededFor` (day, language and zone) gates the reseed; Re-import applies a seed edit at once.
- Every string is a key in the integration's own `i18n/<lang>.json` (`localizeSample`, server only), calendar names included unless renamed. A sandbox takes `Accept-Language`; a Settings switch sends the language and re-imports (`demo/client/language.ts`), but not for a region alone.

## Integrations & Sync
- `Integration` (STI) subclasses are listed in `registerIntegrations.ts` in display order, with statics `label`, `description`, `logo`, `onePerUser`, `developmentOnly`, `discoversSources`, `docs` (its page under `docs/`, checked by `Integration.test.ts`).
- The connect dialog links the guide by `docs` at the start of its footer, the same place for every provider, so none places it by hand.
- **What an integration can do and hold**, two value objects each integration declares itself, as nothing is assumed (only a real subclass derives, Google from CalDAV): `IntegrationCapabilities`, what it can do (`entries.create/edit/delete/rename/statuses/attach/move`, `sources.create/delete`, `availability`; `in(source)` turns writes off for read-only sources; `statuses` are the `TaskStatus`es a task can hold there, which the status menu, the editor's calendar picker and the move preview ask; `floating` whether a time can be a wall clock there (not Google, Notion or Tempo), which the zone picker and the move preview ask; `attach` is off when upstream drops client-written attachments; `move` keeps an entry in place across the integration's own calendars instead of re-creating it, so what Mitra does not show stays), and `IntegrationOwnership`, which entry fields it holds and who owns each, `'upstream'` (a re-import brings it back) or `'mitra'` (lost with the integration), keyed by `Entry` field name: `new IntegrationOwnership({ due: 'upstream', rank: 'mitra' })`. `end` is a length: where none is held (a free Todoist account) `Entry.fit` makes a timed entry a moment and an all-day one a single day, and the editor, the resize handles and the drags make none. Ask, never read a record: `holds(field)` (unheld fields are hidden and refused), `ownerOf(field)`, `ownedBy(owner)`; code writing a field upstream asks `ownerOf(field) === 'upstream'`.
- A source reads its integration, so it answers `capabilities`, `ownership` and `canHold(type)` itself (`@include`, §Backend), and `writable` (enabled, and creating where it is not read-only). A new entry comes from its calendar, `source.draft(init)`: its default type, untitled, fitted, with the account's default reminders where it keeps them (§Reminders & Push); `entry.blank` is a draft nothing was typed into, which is never saved and is discarded on close.
- Engines read entries through `Integration.syncedEntries` (excludes availability), never bare `em.find`.
- Every engine is a `SyncEngine` (discovery and writes) that reads its changes one of two ways, as a `SourceSyncEngine` (`syncSourceEntries`, one calendar's changes: CalDAV, ICS, Tempo) or an `AccountSyncEngine` (`syncAccountEntries`, every enabled calendar's in one read, where the provider's cursor is the account's: Todoist), and the two part in `Integration.syncSources` alone, which an account engine's import of one calendar takes through all of them. An account's mark is `Integration.syncState`, never on the wire.
- Source create/delete routes check the capability, then call `SyncEngine.createSource`/`deleteSource`; renaming needs none.
- **Providers**:
  - **CalDAV** (`caldav/CalDAV.ts`): lists the calendars of the address given (`calendarsAddress`: a principal's home set, or the address itself when it holds calendars), since tsdav's discovery always lands on the login's own principal; a bare host, a failure or Google falls back to it. **Google** extends it with OAuth (`refreshToken`, `withheld`); Google drops `RELATED-TO` and `X-` properties, so its ownership is CalDAV's `without('relations')`, and drops client-written attachments, so `attach` is off and `CalDAV.writesAttachments` omits `ATTACH` lines; shared calendars must be enabled at `calendar.google.com/calendar/syncselect`.
  - **Mitra** (`mitra/MitraCalendar.ts`): stored locally, `syncInterval = Infinity`, uri `mitra://local` (one per user). `fetchSources` returns the stored sources unchanged (`[]` would delete them all) and re-import is a no-op. Participants are a record only (nothing is delivered).
  - **Demo**: `MitraCalendar` plus the sample, dev only, reseeding in `syncSource` when the day, language or home zone changes (paced by presence alone, so a settled home zone is followed within 10 s).
  - **Notion** (`notion/Notion.ts`, REST `Notion-Version: 2026-03-11`, PAT): sources `notion://{dataSource}/{view}`; membership query plus a `last_edited_time` delta; no recurrence, reminders, location or time zone (`timeZone` always null). The description syncs as Markdown through `NotionMarkdown.ts`, replacing only replaceable blocks and round-tripping cleanly. A picture on its own is an `image` block: external ones round-trip as `![caption](url)`; Notion-hosted ones (`file`, a link signed for an hour) are read as `![caption](/api/notion/blocks/<id>)`, served by a redirect to a fresh link (`Notion.fileUrlOf`, `notion/server/notion.ts`), and never rewritten: a write skips the block the text names, so it stays, though above the appended text. Self-relations map to `PARENT`/`FINISHTOSTART`/`X-NOTION-*`; view filters pre-fill new tasks.
  - **Todoist** (`todoist/Todoist.ts`, API v1, personal token; `entries.move`, so a task changes project in place): projects are task calendars (`todoist://project/<id>`), one `/sync` per cycle for the account (`*` while a calendar imports, plus 12 weeks of completed tasks; else the token's delta, which says deletions and completions, so nothing goes for missing from it). A date is the schedule (a day, floating, or fixed in a zone), a duration the end or the estimate, a deadline the due date. The plan decides two fields: `credentials.deadlines` and `durations` come from `user_plan_limits.current` (Free has neither), `ownership` holds `due`, and `end` and `estimate`, by them, and no length is written without durations; every sync discovers first, so a plan that changed what Mitra holds reads every task again. Two states only (`statuses` To Do and Done). A project keeps its Todoist color (`Todoist.colors`), except the default `charcoal`. Repeats stay Todoist's: a task shows at its next date, its rule unshown (Mitra holds none). Relations are Mitra's, a subtask's parent mirrored to `parent_id`. Writes are Sync commands of only the fields that changed, so priority, labels and sections stay, then the task is read back (`GET /tasks/<id>`): a closed repeating task returns open at its next date, and a subtask joins its parent's project, whose calendar the entry follows. Limits: 1000 incremental and 100 full syncs per 15 minutes.
  - **ICS feeds** (`ics/`): one feed, one integration, one source; `webcal` becomes `https`; conditional GET plus a body hash.
- Read-only: `Source.readOnly` from CalDAV's privilege set; the editor shows selectable readonly text and hides mutations.
- **Pacing** (`SyncPacer.ts`): the largest of presence (10 s online, 5 min away), the provider's interval, or 60 s after a failure. Coming online syncs at once. No "Sync now".
- **Vocabulary**: Connect (auth and discovery), Import (first fill of a source), Sync (background), Re-import (read again from scratch). "Fetch" is code-only, "Refresh" means reloading discovery.
- **Import** (`integrations/server/Importer.ts`): `apply` saves credentials and sources and returns at once (`importedAt: null`); `Importer.start` drains in the background with a forked EM, emitting `'sources'` per pass, locking per pass. `importedAt` is set only on a complete pass (max 20). Re-import discards entries and answers 202.
- **CalDAV traps**: multiget falls back to single GETs on 404; `writeDate` keeps the authored form (TZID or UTC) and a series' start shift moves its overrides' `RECURRENCE-ID`s; all writes go through `writeResource`, which retries a 412 once; `updateEntry` mirrors changes only after the PUT succeeds.

## Moving and Copying Entries (`sources/server/SourceMigration.ts`)
- Three phases: copy into the target (collecting old → new uids), repoint `EntryRelation.targetUid` (`user.repointRelations`, the user's links alone), delete the originals. No cross-provider transaction: a failed copy rolls back before deleting; a failed delete leaves duplicates, never loss.
- A copy (`keepOriginals`) skips the delete and mints uids; it repoints only the copies' own rows. Read-only origins copy but never move.
- Lock with `Integration.exclusivelyAcross(ids, work)` (sorted, deduplicated).
- The preview (`MigrationVerdict.of(entry, target)`, `migration/MigrationPlan.ts`, shared with the ICS import) splits blockers from losses by the target's capabilities and ownership: a migration converts and drops what an edit refuses. `entry.canMoveTo(target)` validates a copy placed in `target` for the editor's calendar picker and the table's move, so they offer only what the server would take. Series need recurrence or `flatten: true` (366 days of occurrences). `data.raw` never travels; exclusions travel as `exdates`.

## Entries
- `Source.entryTypes` lists `event`/`task`; availability is everywhere, gated by `capabilities.availability`. `EntryType` is a value object that says which fields an entry of it has (`holds(field)`); setting `Entry.type` strips what the new type can't hold.
- **An entry answers what it allows**, from its type, whether it is saved and its calendar's say: `editable`, `deletable`, `copyable`, `holds(field)` (its type has it and its calendar keeps it), `canEdit(field)` (held and editable; the heading needs `rename` once saved, attachments `attach`, participants the organizer), `statuses`, `types`, `convertible`, `floatable`, `externalLink`. Views ask these inline and never combine `type`, `persisted` and `source.capabilities` themselves, nor keep a getter of their own that only forwards to the entry; a question about another calendar (`canMoveTo`) is the entry's too.
- **Vocabulary** (UI and docs): the **schedule** (`start`/`end`), the **constraints** (**due date**, **estimate**; never "deadline"/"duration"), **planning** (fitting unscheduled tasks), a **moment** (a start without an end).
- **Edits are patches** (`EntryPatch`, a model): omitted fields keep existing values, `null` clears, defined values set; boundary converters parse formats. `Entry.patch(patch)` applies updates, dropping unsupported type fields and converting replaced estimates. Client sends `EntryPatch.of(entry, fields)` (shared across recurring series, or occurrence-scoped); routes build `existing.edit(patch)`, or `source.create(patch)` for a new entry, the same change without an `entry` (`EntryChange`), a `Validatable` (`change.validate({ graph, scope })` yields the organizer rule, the patch's, the calendar's and the relations', on the graph `user.getRelationGraph(em, change.related)` gives; the route first sets the calendar it ends up in, `change.edited.source = await user.getSource(…)`, which proves it the user's) that saves itself (`save(em)`, fitted to its calendar): in-place updates or re-creations across calendars/types (create-first, then delete); `recreates` keeps a move in place where the integration moves its own (`entries.move`), the engine's `updateEntry` then seeing the new `sourceId`. Relating and unrelating are edits whose patch carries the new relations. Entries contain no `null`.
- **Where an entry lies** is an `EntrySpan` (`entry.span`: start, end, all day, estimate, due), which a gesture, a preview, a duplicate and a drag's create or resize move apart from the entry (`EntrySpan.timed`/`allDay`, `movedBy`, `resized`, `equals`) and the entry takes back whole (`entry.adopt(span)`); `entry.spanOn(day, zone)` is its span on another day. The edits that read more than the dates (`scheduleAt`, `unschedule`, `moveStart`, `setEnd`, `setAllDay`, `setTimeZone`, which trade the end for the estimate, carry the due, drop reminders or follow the type) stay the entry's. Where nothing says how long or at what hour, a time comes from `ScheduleDefaults` (the account's length, registered by `DefaultDurationSetting` as `ReminderDefaults` is; the working day's 9:00 and a due's 17:00), never a number written at the call.
- **Task model**: `Entry.open` is a task not closed (`closed` is false for an event, so no caller checks the type beside it); the `progress` setter keeps progress and status coupled (RFC 5545 §3.8.1.8): full progress closes, less reopens a done task as Doing where the calendar has it, none clears, while `percentComplete` stays a plain field, since every engine writes it after the status; the `done` setter is the toggle. End and estimate exclude each other (`scheduleAt`/`unschedule` convert); drags move the schedule, never `due`. A moment (`Entry.point`) has no duration, a series of moments included. `setAllDay` converts `due` too (VTODO needs matching value types).
- **CalDAV tasks**: `DTSTART`, `ESTIMATED-DURATION`, `DUE`; never `DURATION` on a VTODO. Each property means one thing whatever else is beside it: DTSTART + DUE without a length is a moment with a due date (how Mitra writes one, and how OpenTodo spells a planned day with a deadline), never a block spanning the two.
- **Time zone**: one per entry for all its dates, an `EntryTimeZone` (`Entry.timeZone`, kept beside `TimeZone` in `features/time`, which the zone picker offers too): none follows the viewer, `EntryTimeZone.floating` is wall-clock time (`Entry.floating`), else a zone kept in the spelling it was written with (engines spell some differently), whose `clock` is where its wall clock is read as stored (UTC when floating; the browser holds floating times in `TimeZone.local`). `Entry.zone` is the `TimeZone` its times are written in. `setTimeZone` keeps the clock times. `TaskStatus`, `Transparency` and `Visibility` are value objects, their columns keeping their CHECK constraints (`@enum` with a `Mapper`). An occurrence's edit travels as an `EntryPatch` like any edit (`EntryPatch.occurrence` names its fields), to the occurrence's address.
- Start-less recurring tasks anchor on `due`; the views show only the current occurrence (`occurrences.current(zone)`, in the viewer's zone), and scheduling one detaches it (`'this'`).
- **Planning** (`mitra-planning`): Overdue (an open one-off task whose `lastDay` passed; the drag ghost excluded) then Unscheduled (manual order, then due; a task not saved yet last of the open ones, since a row moved in the DOM closes its editor; also the drop target that clears dates). Only one-off tasks unschedule (`Entry.unschedulable`).
- **Manual order**: `Entry.rank` (`EntryRank`, fractional), Mitra's own, never synced; only changed ranks are sent (`PUT /entries/ranks`); a series ranks through its master; re-created entries carry `rank`. Reordering leaves the list into `EntryDragController.beginExternal`.
- **Duplicate to other days** (`DialogDuplicateDays`): independent copies, never a rule. Each copy's span is `Entry.spanOn(day, zone)`, whole days on the clock its times are written in (an unscheduled task's due moves, a scheduled one's stays), each saved through `EntryStore.duplicate`; the days the entry covers are disabled in its picker, never chosen. Opened in the top layer, outside the chip, the dialog wears the entry's accent itself (`entryColors` over the entry's color, else its calendar's), as the editor's own dialogs inherit it.
- **Editor dates** (`EntryDetailsWhen`): one row per field (start, end or estimate, due), then zone and repeat; the All day toggle sits on the row in use; ✕ on a start unschedules, on an end makes a moment.
- `GET /entries` also carries undated entries and open tasks overdue before the window (`user.filterEntries` with a `range`), and every recurring entry once, its overrides nested (`Entry.overrides`); the browser expands them (§Recurrence & Routines).
- Drawer tabs (`design/Tabs.ts`) always scroll LTR (panels reversed in RTL): Chromium misplaces a `view()` timeline in a scroller whose origin is its inline end. They follow the panel whose start the strip rests on, read on every `scroll`: Chrome's find in the page jumps the strip with no `scrollend` and no snap events.

## Operations (`infrastructure/operations/`)
- Every JSON endpoint is an operation: one class per file in its feature's `server/`, `Operation<Parameters, Result>`, whose `run({ em, user })` does the work and throws what it refuses. Nothing is injected: an entry's calendar is `entry.source`, joined as `user.getEntry` loads it; another calendar comes through the user (`user.getSource`); the emitter is a module, `this.logger` is tagged with the class name.
- **Parameters are a class** (unexported `Parameters` above the operation, or a domain class such as `EntryPatch`) named by `@operation(Parameters)`; members declare `@validation`, `@description` and, where the written form differs, `@converter`, keeping the wire's names (`id`, `start`, `sourceId`). Both transports read them through `Operation.fromValues`: read as written, built through the converters, judged after. A body the reviver already built (`EntryPatch`) is taken as is, path and query joining it; a body of its own is the parameter `@http({ body, type })` names (`ConnectIntegration`, `ImportIcs` as `text/calendar`).
- Facts are decorators: `@operation()` registers, `@label`/`@description` (`@a11d/metadata`) describe, `@http({ method, path, status, body, type })` routes, `@updates('entries' | 'sources')` declares what a run that succeeded updates for its user, which both transports dispatch after `run` (`updates.dispatchFor(operation, user)`, reading it back with `updates.of`), never the operation itself. The same `updates` (`infrastructure/realtime/Updates.ts`, shared so operations can wear the decorator in the browser) is the one stream the event stream subscribes to, as `http` is a decorator that `http.get` reads: `subscribe(listener)` answers the function that unsubscribes it.
- **The browser calls operations** from `#operations`, typed by their parameters and result: `RenameSource.call({ id, name })` fills the path, sends the rest as a GET's or DELETE's query, else as the body. Its build strips `run` (`operationsWithoutRun`), so what only `run` imports stays on the server; what runs at load must be browser-safe (`process.env` only in `run`), as `bundles.test.ts` checks. `Api.ts` keeps what is no operation (uploads, the Google redirect); what the page learned of the server is `session` (`http/PageSession.ts`: `user`, `settings`, `instance`, `keepUser`).
- `app/operations.ts` is `#operations`, re-exporting every operation; the router mounts a fixed path before a parameter in its place (`/entries/ranks` before `/entries/:id`), after the feature routers. No operation imports another.
- Refusals: `ValidationError` 400, `NotAllowed` 403, `NotFoundError` 404. Shared steps belong to a domain concept (an entry edit's are `EntryChange`'s), never a base; what stays written out in each is the claim of files, the flush and the read-back. `ChangeTimeZones` stays a base. `context.user` is the user as the request's `em` holds it (`req.user` outlives the request), so an operation changes it and its flush saves it.
- An occurrence's change and deletion are operations of their own at `/entries/:id/occurrences/:occurrence?scope=`, naming the date through `occurrences.existing(occurrence)`; an old tab's `?recurrenceId=` is refused by `staleTabs` (409).
- **The environment** is `environment` (`infrastructure/server/Environment.ts`, so `bundles.test.ts` keeps it out of the browser): every `MITRA_*` variable read, defaulted and checked once as the server starts; a test builds its own (`new Environment({ … })`). `Oidc.of`, `GoogleOAuth.of` and `FileLimits.of` build from it, a shared class learns what it needs from what the server registers (`GoogleCalendar.from(() => environment.google)`), and nothing else reads `process.env` (`orm.ts`'s test switch aside). What the browser learns is the `Instance` model `GetMeta` answers, kept as `session.instance` (`displayName`, `stale`; the running release alone until the server answers, and what it said last when it does not), never a field of the environment spread onto it.
- Only what answers without JSON stays a router: redirects (OIDC, Google, Notion), the event stream, health, files.
- Tests: one per operation beside it, through its `call` on an `OperationServer`, its tool through `server.tool(name, args)` in an `as a tool` block; viewers in other zones from `entries/server/viewers.testing.ts`.

## Agents (MCP, `features/agents/`)
- The agents' transport, as `infrastructure/http` is the browser's. `/api/mcp` serves MCP (Streamable HTTP, stateless, `responseMode: 'json'`; a request without a protocol version gets the SDK's 2025 fallback, answered as SSE) behind the API's authentication. Single-user mode has no credential, so a foreign `Origin` is refused (403), as is the demo; `MITRA_MCP=off` closes it (404).
- Tools are the operations wearing `@tool({ name, annotations? })`, their arguments `validation.schemaOf` their parameters; hints follow the `@http` method (`tool.annotationsOf`), stated only where they differ. A tool answers with the API's own serialization (a list under `items`), as structured content and as text: no agent-only shape. Refusals answer `isError` with text a model can act on (`toolResultOf`); there is no agent-only error type.
- **Access tokens** (`identity/AccessToken.ts`, `mitra_` plus 32 random bytes in hex, stored as its SHA-256): `Authorization: Bearer`, read by `accessTokenMiddleware` on `/api/mcp` only, before `authMiddleware`; a bad token is 401, never read as none. A `read` token is offered only `readOnlyHint` tools. Managed under Settings → AI → Access tokens only where people sign in: made in one dialog, shown once in the next (`DialogNewAccessToken`, `DialogAccessToken`); `lastUsedAt` written at most once a minute. OAuth would join beside them, not replace them.
- **WebMCP** (`agents/client/webMcp.ts`): where `document.modelContext` exists, the page registers the endpoint's tools over plain JSON-RPC with the session cookie; the browser bundle holds no MCP SDK.
- **Reading**: `ListEntries` is the browser's; agents ask `get_overview` (no route), the same query with each repeating entry unrolled by the browser's own code into occurrences (`occurrence` = its original start, never an index), beside `availability`, `overdue` and `unscheduled`, over every enabled calendar (hiding is the app's view) and without a provider's busy copies. `get_context` gives the home zone, how the user reads dates (the settings' locale, its calendar, week start, weekend, today in both forms), the user's addresses per integration, and per calendar `holdsTypes` and `defaultFor`.
- **Writing**: an instant with its offset, a day only with `allDay: true` (an all-day end being the day after), or a wall-clock time with its zone (RFC 9557, `2027-03-02T09:00[Europe/Berlin]`, read by `Temporal.ZonedDateTime.from`); anything else is refused. Server date math is Temporal with an explicit zone, never milliseconds. Availability is written like any entry; participants whole (`Participants.converter`), the user leading as organizer; relations as the entry's whole owned list by `uid`, or one at a time (`RelateEntries`, `UnrelateEntries`, tools only); an occurrence's edit refuses relations. What agents may not write has no written form (files convert without a `schema`).

## Calendar Views
- **Weeks follow the locale** (`DateTime.weekStart`): every grid starts there, never at `dayOfWeek === 1`; a locale switch rebuilds the buffers.
- **Whole weeks** (`WholeWeekSetting`, per device): the week view lays out seven columns over its width and snaps only to the week's first day (`mitra-day[data-week-start]`), where it anchors a date.
- Views: `mitra-days` (week), `mitra-weeks` (month), `mitra-months` (year), `mitra-timeline`, `mitra-table`.
- **`EntrySegments`**: `for(occurrence)` memoizes per-day segments; `timedOn(day)` clusters; `runsIn` reads a per-cohort day index; lane packing is unbounded, overflow clipped behind a fade; ties order by heading (`laneOrder`), never arrival. Cache `.dayValue` in hot loops.
- **Drag** (`EntryDragController`): create, move, resize (0.25rem handles). Nearness snapping (`DayCells`: hairline boundaries assign to adjacent cell) gated by `places()` (grid minus sidebar). Moves preserve grab offset (planning chips anchor at start). Never `setPreview` an unchanged span (`span.equals`) to avoid per-frame repaints. Drag steps notify via `EntryStore.notifyMoved` (views, chips, and badge/connector hosts), never `notify()`; unchanged day segment lists are reused so Lit skips rendering. Local draft in `EntryStore.draft` (id 0).
- **Scrolling** (`CalendarScrollController`): date-anchored; a navigation also arrives on the cross axis (today's now line, else midday), but a step (`PageCalendar.step`, the arrows) keeps the time in view; a scroll echo is told apart by identity. Zoom (`DensityController`: Ctrl+wheel, rail wheel, pinch).
- **Time zones**:
  - **A zone is a `TimeZone`** (`features/time/TimeZone.ts`) past the Intl/Temporal boundary (the platform has none since Temporal dropped it). `of` interns one instance per zone through Intl's spelling (Chromium and Node spell zones the CLDR way, Firefox the IANA way) and throws on unknown ids, so `equals` is identity; never Temporal's, whose native engines merge zones CLDR keeps apart (Oslo into Berlin). `parse` reads untrusted values. Past that boundary a zone is always a `TimeZone`, never its id: occurrences (`standing`, `current`), rules (`RecurrenceSet`), an entry's `clock`, a device's zone (`TimeZone.Mapper`, `TimeZone.converter`) and the reminders' reader; `.id` only where Temporal or Intl takes it.
  - **Home and here** (`UserTimeZones` on `User`): account stores home and added zones, each optionally named; here (device zone) anchors the grid and is never stored. Home is set once from the first device (`settle`) and replaced by `makeHome`, never removed; naming here persists it. Server applies one command per request (`/user/time-zones/…`). `User.timeZones` is a value object persisted via dedicated `Mapper` and `converter`. UI indicators: house for home, pin for device zone.
  - **Names** (`TimeZoneName`, Intl only): reader's abbreviation, else zone's region (Latin script), else place (`shortGeneric` without locale pattern), else offset. Zone region resolves via `getTimeZones()` over all regions.
  - **Picker** (`TimeZoneDirectory`): zones grouped by name and both yearly offsets, the reader's region first; a row stands for here or home, else CLDR's golden zone (`TimeZone.isGoldenIn`: Toronto in Canada, New York elsewhere), which Intl hides; it takes and gives `TimeZone`s, reads home and here from `TimeZones` as it opens, and an entry's editor lists a floating time first where the calendar keeps one or the entry floats (`floatable`, picked as `EntryTimeZone.floating`, keeping the clock times), named "Same time everywhere" with `globe-off`, which the editor's zone row also wears, faded like the viewer's own zone; `npm run zones:generate` writes `goldenZones.json` (current names only, both spellings).
  - `TimeZoneLaneController` folds the extra columns (the anchor never folds). Each is exactly `--zone-width` wide, opening to the widest label, a time or a zone's name (`--zone-lane-width`, measured when their text changes), so `--time-axis-width` is CSS's own (`--_axis-rest`, what never folds, is measured) and the days follow the lane in the same frame, never a measurement behind; while it moves, Days re-anchors the date every frame and reads no offset back (`suspended`).
- The week's all-day lane uses explicit row tracks (`repeat(var(--slots), var(--slot-height))`), never auto-flow.
- **Chip heading** (`EventSegment.ts`): two layouts switched by the space toggle `--inline` (no `if()`: Chromium only). The when line is `DateTimeRange.format()`, never hand-assembled; `dated` adds the day off the grid.
- **Month** (`mitra-weeks`): week rows with subgrid columns and CSS density scaling; `.entries` at `z-index: 2` over connectors; per-week layouts memoized; an ISO week rail (labelled by each row's Thursday); zoom 2–9 weeks with a quantized settle.
- **Year** (`mitra-months`): a strip of mini months with subgrid lanes; `overflow-anchor: none`.
- **Timeline**: open scheduled tasks, one row each, virtualized by plan; routines show due occurrences only; sticky `.jump` buttons.
- **Table** (`calendar/client/Table.ts`): a `TableWindow` from today, no paging; the unbounded window lists each recurring entry once, as its first occurrence (`occurrences.anchored`, scope `'all'`).
  - A `div[role=grid]` with subgrid rows, never `<table>` (lit foster-parents out of `<tbody>`; Chromium drops subgrid under `content-visibility`).
  - Sticky header row (not cells) and sticky `.actions`; a hidden `.anchor` row holds each column's widest content.
  - The resize line lives inside its handle, never `position: fixed` (`.calendar` has `contain: layout`).
  - Cells reuse editor components; batch edits run series occurrences one by one; `TableRowComponent` keeps a field's keys from the grid.

## Routing & URL
- One route (`PageCalendar`, `/:view`), overlays and filters as query parameters (`?date=`, `?selected=`, `?settings=`); `CalendarLocation` parses and writes them; today is omitted.

## Commands
- One class per action extending `Command`; facts are `abstract readonly` fields, getters only for live state; always run through `dispatch()` (absorbs `DialogCancelledError`). Context comes from `Mitra.instance.calendar`. Header buttons are the commands themselves (`PageCalendar.commandButton`).
- **Dismissing a dialog** rejects its `confirm()` with `DialogCancelledError`, ending whatever opened it, so no caller catches it to go on. A dialog whose dismissal is an answer (a scope, a deletion, a rename) says so in its `cancellationAction()`; one nothing awaits ends at `Mitra`'s `unhandledrejection` listener, never in the console.
- `commandInstances()` caches instances and rebuilds them on a language change; never `new` the registry per render.
- **Palette** (`mitra-command-palette`): a `<dialog>` around an inline combobox, opened by `/`, Ctrl+P, Ctrl+K. Its `commands` is a function, asked only while open. One search rule for the app (`termsMatch.ts`). Entries come from `GET /entries/search` (`user.filterEntries` with a `search`) as stored, with their overrides, hidden calendars included (dimmed here and in the relations picker; opening one shows its calendar first, `Calendars.show`, as the editor opens only on a rendered chip); the palette shows each as the occurrence standing for it now (`occurrences.standing(zone)`) and opens it by its key.
- **Editor intent** (`EntryEditorIntent`): `openDraft`/`requestOpen`, anchored on hosting surfaces (a scheduled entry's request is the view's, never a `dated` chip listed beside it, as `reveal` sends it); `settle` clears unmatched intents; span edits re-request after render and dispatch `reveal` (scroll to it, or open the Planning tab).
- **Keys** (`PageCalendar.handleKeyDown`): ignore fields, IME composition, chords and anything pressed in an open popover or dialog (`startedInOverlay`). Read keys through `KeyPress`, never `e.key` alone: the typed letter on Latin layouts (AZERTY, QWERTZ), the physical key where a layout types another script (Persian).

## Settings
- One class per preference beside its feature (`Setting.ts`); `app/settings.ts` only orders them. Settings own defaults and options; domain code takes preferences as parameters. The server bundle excludes client settings (`bundles.test.ts`).
- Storage: `userStorage` (`User.settings`) or `deviceStorage`; only deviations are stored (`undefined` removes, `null` is an explicit none). `UserSettings` sanitizes without importing settings.
- Each setting is a card (a field's tint and hairline, `SettingRow`) beside an unfilled rail. `details` renders below a hairline in the same card; a `ul` there lays items on the card's own columns (glyph, `.text` with `.label`/`.hint`, `.end` with a `.chip` and an options `mitra-menu`), so a list needs no layout of its own. A list with an action is a setting of its own, the action its control (`DevicesSetting`, `AccessTokensSetting`); something made and shown once is a dialog pair, never a popover or an inline row. Relative times tick through `ClockController`.
- Scroll containers need inline padding, or they clip focus rings. Settings add palette verbs (`settingCommands()`). The dialog is searchable, two-pane, opened from the sidebar, the palette or Ctrl+, (`PageCalendar.openSettings()`).

## Recurrence & Routines
- A recurring entry holds an RRULE (`Recurrence` value object, one `recurrence` column holding its RRULE through its own `Mapper`, and the same RRULE text on the wire both ways through `Recurrence.converter`) and expands on read from its own fields, never its stored .ics (the sync reads EXDATEs into `exdates`). An override (`RECURRENCE-ID`) is a row of its own (`recurringEntryId`, `recurrenceId`), read with its recurring entry as `entry.overrides`, never stored on it.
- An entry's dates are `entry.occurrences` (`EntryOccurrences`), lazy and in order: a one-off entry yields one `EntryOccurrence`, a recurring entry one per date its `RecurrenceSet` yields and an override in place of the date it takes over (`within(window, overrides)`, `standing`, `current`, `anchored`, `at`, `yields`). An occurrence shows its `entry` (the one-off, the recurring entry, or the override) and knows its `recurringEntry`; it answers the date facts (`scheduled`, `lastDay`, `inclusiveEnd`, `overdue`, the reminder anchor), which an `Entry` reads off its own single occurrence, and its `key` (`<recurring entry id>__<UTC ms>`) is the same in every zone and once an override takes the date over. Windows are `DateTimeRange`s. Client and server share expansion logic (`bundles.test.ts` verifies separation); queries are scoped to a `range` of `user.filterEntries`. Use "recurring entry" terminology, not series or master.
- **The browser expands** (`EntryStore`): the store keeps stored rows only (overrides flattened out of their recurring entry) and composes `EntryStore.occurrences` for the window it was fetched for (each recurring entry's first without one). Views, segments, routines, the table and planning take `EntryOccurrence`s, the views and planning `EntryStore.shown`: what a lens registered once (`EntryStore.showing`, the hide-done setting's) leaves, never filtered per view; chips key by `EntryStore.identityOf`. Nothing edits a recurring entry through a yielded date directly: `EntryStore.editable(occurrence)` creates an override row (`occurrence.override()`, keyed by occurrence key) modified by drag, editor, and batch edits, prompting for scope on save. Clean overrides persist across refetches while yielded by rule.
- RFC 5545 counts month days, nth weekdays and yearly dates in Gregorian months: use `start.recurrenceDate`/`start.formatAsAnniversary()`, never the display calendar's `start.day`.
- A rule's parts are value objects: `freq` a `RecurrenceFrequency` (one instance per code, `days`, `format(every)`), `byday` `RecurrenceWeekday`s (`Monday`…, `nth(-1)` the last; `week()` and `workdays()` follow the locale's first day and `getWeekInfo().weekend`, Saturday to Thursday in Persian), `until` a `RecurrenceEnd` (UTC calendar day: `of`, `before`, `parse`, `toRRule(allDay)`; on the wire as UTC midnight). Unedited RFC parts (`BYSETPOS`, `BYMONTH`, multiple month days) preserve in `rest` for lossless round-tripping; displayed as "Repeats" in editor and overwritten on edit. Models hold plain data, never a Temporal object: the API client `structuredClone`s request bodies, which native Temporal refuses (Node tests run on the polyfill, which clones), and dirty checks compare deeply, where `PlainDate#valueOf` throws. Their `format` defaults to `Localizer.locales.current`, imported explicitly: the global exists only once something imports @3mo/localization, and under Node the Localizer falls back to `navigator.languages`.
- A day in an address or a stored key is `date.isoDate` (ISO whatever calendar it reads in, `calendar/client/DateTime.calendar.ts`).
- Scoped edits are the occurrence's: `occurrence.edit(patch, scope)` and `delete(scope)` return an `EntryOccurrenceChange` (what to rewrite, exclude, create or remove), pure, in an `EntryOccurrenceChangeScope`, which `change.save(em, from, to)` writes, creating first. 'this' detaches, 'following' splits, 'all' rewrites the recurring entry, adopting the edit's duration (none for a moment). A `sourceId` in the patch moves what the scope reaches; the client must send it. Only 'this' may drop the date the rule repeats from (`EntryPatch.validate`). An edit that takes a date between the all-day lane and the hours, or into another zone, moves the recurring entry by the same days to the edit's time in its new frame, never by the distance between a day and an instant; the client names the date as its recurring entry stores it (`occurrence.storedRecurrenceId`), whatever the edit made of the date.
- **Routines** collapse dense series into one ribbon mark per day in month and year views, pooled by source and heading, when the stride is under a row unit (week slack 1.0, month 1.25) with at least 4 instances.

## Reminders & Push
- An entry's reminders are an `EntryReminders` (minutes before the anchor, each once, in order, none rather than an empty list: `normalize`, `adding`, `without`, `earliest`), in a JSON column (`EntryReminders.Mapper`) and on the wire (`EntryReminders.converter`); the account's defaults are a `ReminderDefaults` (`standard` is Mitra's own, which the two settings fall back to), registered for the browser (`ReminderDefaults.from`, in `DefaultReminderSetting.ts`) as `@include` finds a source: `source.draft` starts a new entry with `defaults.for(entry)` (its kind's; none for a day, availability or an entry with no time), and reminders still on them follow a change of kind (`defaults.gave(entry)`), so no state marks a draft. The server registers none: a create naming no reminders starts with `user.reminderDefaults` (`ReminderDefaults.of(settings)`, the rule the browser registers too), and `null` or `[]` names none.
- Reminders count back from `Entry.reminderAnchor` (start, else due for unscheduled tasks); `unschedule()` clears them unless a due remains; closed tasks never fire. CalDAV TRIGGER is `START`, or `END` against DUE for unscheduled tasks (`CalDAV.reminderAnchorOf`).
- The server renders each notification per device (`ReminderNotification.for`) in its `locale` and `timeZone`, via `localizeIn`; the worker only shows it. The body states the time, never a countdown. At most 2 buttons; Done posts `/entries/:id/complete`.
- Push sets `TTL` (anchor + 5 min) and `urgency: 'high'`; `icon` goes to Android only.
- `ReminderScheduler` claims `(watermark, now + interval]`, sets exact timers, persists the watermark, dedupes in memory. Floating times resolve in the device's last zone.
- Devices are listed under Settings → Notifications; `register` keeps the user's `name`; a rotated subscription inherits name and locale (`succeed`). The page re-registers on a locale change.

## Participants
- `Entry.participants` is a `Participants` (an array of `Participant` value objects, normalized: one per address, one organizer), in a JSON column (`Participants.Mapper`) and on the wire (`Participants.converter`, which also names the written form); a copy keeps it a `Participants` (`Entity` copies an array of its own kind as one), and callers ask it (`organizer`, `manageable`, `summary`), never a mirror on the entry. Object equality compares constructors, so every path holds `Participant`s, never plain objects (`Participants.normalize`); `ownership.holds('participants')` (not for Notion); only the organizer edits the list (server-enforced); identity from `Integration.addresses`; CalDAV mapping in `CalDAV.participantsFrom`/`writeParticipants`.

## Files and Attachments (ATTACH)
- **Files** (`features/files/`): `File` is abstract; each holder extends it with its own table (`EntryFile`). Bytes live at `data/files/<user>/<sha256>`, remote files at `sourceUrl`. `UnusedFileDisposer` prunes unreferenced files 24 h after last write.
- **Serving & Capabilities**: Upload-minted IDs are capabilities: `GET /api/files/:id{/:name}` is public (for external calendar clients) and sends `nosniff`, `CSP: sandbox`, `no-transform`. Mitra URLs match by path, never origin. Uploads mount before `express.json()`. Limits: `MITRA_FILE_MAX_SIZE`, `MITRA_FILE_QUOTA` (disabled in demo).
- **Entry Files & Claiming**: `Entry.files` (`EntryFiles`) is stored and sent; `Entry.attachments` is a view over it. Copies/moves mint fresh IDs. User writes claim files before save (`FileStore.claim`): client never dictates IDs, and local bytes must belong to the user. References resolve by ID, link, hash, or Mitra URL (`File.refersTo` -> `File.resolve`).
- **Editor & Sync Invariants**: Uploads and drag-and-drop require `capabilities.entries.attach`. Pre-upload hashing skips duplicates and keys optimistic rows; save waits for row animations (`data-animated`) to settle. The row subscribes to `EntryStore` (a save or sync changes the entry in place). Removing a chip is `Entry.detach(file)`: the file goes, and with it every link or picture of it in the description (`MarkdownLinks.without`); the row's other button is `Entry.embed(file, origin)`, a picture or link at the end of the text by the public URL, once (`embeds`, `MarkdownLinks.mentions`). CalDAV diffs `ATTACH` lines by address, preserving matched and inline `BASE64` lines verbatim. Held upstream by CalDAV, ICS feeds, Google (Drive, read-only), and Mitra; unsupported by Notion, Tempo, or availability.

## Relationships (RELATED-TO)
- `RelationType` values; stored on the dependent entry by `uid` (`EntryRelation`, a row told apart by its line). `Entry.relations` is an `EntryRelations`, `@children` saved on flush: the lines an entry is set to become its rows, an incoming one never, and `undefined` leaves the rows as they are, so a provider that cannot say changes nothing; absent is unknown, an empty collection is none, the wire an array. Written upstream as the entry's owned relations alone (`updateRelations`), outside entry dirty checking. Its views of this entry's side (`shown`, `sections`, `edges`, each `Relation`'s `section` and `edgeOf`) take the uid when asked, as an entry's uid can change after its relations arrive; CalDAV diffs `RELATED-TO` lines. `ShiftStrategy` moves dependents. Rebuilding `entry` must hold `entry_relation` rows.
- **Reads carry both directions; writes only owned lines**: reads and write responses attach each entry's own rows and those pointing at it (`incoming`), each `Relation` linked to its `target` however far (`user.getRelationGraph(em, uids).attach(entries)`: both directions from the one graph, which reads outward from the uids a step at a time until no link leads further, never the user's every link, the entries reached linked in through `EntryRelations.link`, each once, where first reached, so the JSON stays a tree). `EntryRelations.validate` judges a candidate list on `graph.replacing(entry, relations)`, the graph as the write would leave it. The browser's graph builds from the store (`RelationGraph.of`), so rollups, ancestors and shifts reach past the window. Writes send `EntryRelations.writeConverter` (owned lines, no targets).
- **Where an entry stands** is `entry.hierarchy` (`EntryHierarchy`): its `children`, `parents`, `descendants`, `predecessors`, `completedAncestors`, `rollup` and `progress` (the rollup's, else its own), `canBlock(other)` and `shiftOptions(change)`, read off the one graph the browser registers (`EntryHierarchy.from(() => EntryStore.graph)`, rebuilt when the store's entries change), as `@include` finds a source; on the server, where none is registered, an entry stands alone. No static reads the graph for an entry.
- **What a hierarchy leads to is planned by the entry** (`entry.hierarchy.planShift`, `planDeletion`, `planClosing`, `planCompletion`, each an `EntryPlan`); the browser's `hierarchy` (`relations/client/Hierarchy.ts`, one object holding its own state) asks the scope a gesture reaches, applies the plans through the store, and offers the follow-ups when a task closes, listening on `EntryStore.whenTaskCloses` rather than replacing a hook.
- **Progress** (`RelationGraph.getRollup`): subtasks and `- [ ]` checklist items count equally; ticking a box edits the description only (`Checklist.toggle`), never status. Tasks only.
- `mitra-markdown[interactive]` numbers checkboxes in document order and emits `check`.
- **Connectors** (`EntryConnections.ts`): routed by grid columns. Into the neighbouring column, a clear pair gets a vertical S-curve, anything closer a `bend` (two arcs of `BEND_RADIUS`), drawn in pure CSS (container units and trigonometry), emitted twice with the wrong twin hidden by a container query. Lane and canvas layers split the edges by realm.

## Availability
- `EntryType.Availability`: repeating windows in the calendar's color, free by default, stored locally, never in `EntrySegments` or routines (`Availability.outside()`), drawn in the week view as `mitra-availability-segment`. Excluded from search, relations, participants, reminders and all-day lanes. `HideAvailabilitySetting` hides it everywhere.
- Busy windows publish to CalDAV as `mitra-availability-<uid>` series (`SyncEngine.publishAvailability`), retried on sync.
- `EntryEditorIntent.shouldOpen` takes an occurrence: its key, its entry's id, or its recurring entry's id, which opens the first one shown.

## Links
- Derived, never stored: read from the description and single-link locations (`MarkdownLinks.of`/`sole`), excluding entry files (`EntryFiles.at`). The editor's Links row only reads; its `li` is always rendered (hidden when empty) so lit never rebuilds the textarea below.
- One linkifier, `MarkdownLinks.marked`, renders and reads; never `marked.use()` (`NotionMarkdown` uses the global instance). `MarkdownLinks.allows` refuses `javascript:`, `data:`, `file:`.
- `mitra-link` (`design/Link.ts`) names a bare address by host, meeting service or app (its own tables).

## Build, Test & CI
- Node 26. `npm run typecheck` (TypeScript 7, the one entry point; `typescript` aliases 6 for typescript-eslint). `npm run lint` (tabs, single quotes, no semicolons, final newline, `max-lines` 1000, no `console.log`). `npm test` bundles `src/**/*.test.ts` for `node:test`, split into shared chunks (`out_test/chunks/`, maps beside them: inlined and unsplit, 187 bundles were 2.6 GB), so a test file's own top level runs after every chunk it imports: nothing a module does at load may count on a shim the test imported first. `npm start` watches; `npm run build` needs `data/`. Scripts run their TypeScript through Node's type stripping, so code they import has no parameter properties or enums.
- **No real services in tests**: external service tests replay recorded responses (`infrastructure/http/HttpRecording.testing.ts`) captured via Docker (`npm run record:caldav` -> `caldav/recordings/`) or a real account (`MITRA_TEST_TODOIST=free|pro=<token> npm run record:todoist`, a second between requests). Requests missing from recordings fail tests. A JSON API names its own placeholders (`HttpRecordingFormat`: server-minted `tokens`, `times`, request `stamps`, `secrets` never kept); a recording keeps every server token made up in its shape (`HttpRecording.madeUp`), so it holds none of an account's ids.
- **PWA icons** (`scripts/indexHtml.ts`): a dedicated `maskable` icon (never `any maskable`) at 50% over `themeColor`; the monochrome mark ships only as `notification-badge.png`, never a `monochrome` manifest icon (Edge paints it black). Notification `icon` is Android-only.
- **Compression**: build-time `.br`/`.gz` served by `precompressed(dist)`; `compression()` for the API must skip `text/event-stream`.
- Docker `node:26-bookworm-slim` → `ghcr.io/a11delavar/mitra`; workflows: `qa.yml`, `docker.yml` (tags; `latest`, `X` and `X.Y` move only for the newest stable tag they cover, so a backport never takes them back), `release.yml` (a backport is never Latest, and dispatches a website build of main), `cleanup.yml`, `website.yml` (`fetch-depth: 0`; moved pages in `astro.config.mjs` `moved`).
- **Changelog**: generated and gitignored (`npm run changelog`, `scripts/changelog.ts` over git-cliff and `cliff.toml`): CI writes it for the image, the release and the site, never a commit. ## Conventions
- Commits: one line, `type: Capitalized phrase` (`feat`, `fix`, `perf`, `refactor`, `docs`, `test`, `ci`, `build`, `infra`, `chore`), stating the user-facing effect; it becomes the release note.
- Tabs, no semicolons, a final newline. License AGPL-3.0-only.
- **Imports**: relative within a unit (a feature, an integration, an infrastructure module, or `app`/`design` whole), and across units through the `package.json` `imports` map, which Node, esbuild, TypeScript and Vite all read. Domain, infrastructure and design directories other units import widely have a barrel, their `index.ts` named by an exact key (`import { Entry, EntryType } from '#features/entries'`); everything else is imported by its file (`#features/time/TimeZone.js`). A barrel runs every module it holds when one is imported, so it re-exports only what other units import, leaves first, and never a module imported for its side effects or a registry (`registerIntegrations`), `#operations` aside. Client directories have none: settings, commands and operations register in import order, and a client barrel moved settings rows. A unit never imports its own barrel; `#design` is for client code (it registers every control). An import block runs packages first, then `#` modules (`#operations`, `#design`, `#features`, `#integrations`, `#infrastructure`, `#app`), then relative ones, each group keeping its own order; entry points and registries (`app/client.ts`, `app/settings.ts`, `app/operations.ts`, `registerIntegrations.ts`) keep theirs, since import order is the order they run and register in.
- No return type TypeScript infers; state one only where inference falls short (recursion, a tuple, a literal that would widen, a contract subclasses override).
- No real people's names in code, tests or seeds; role placeholders (`organizer@example.com`).
- Domain-driven, object-oriented: behavior on aggregates, value objects and collections, not loose helpers.
- Comments: one or two sentences on a non-obvious invariant, protocol edge or platform bug; no narration.

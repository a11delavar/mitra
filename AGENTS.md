# AI Agent Instructions

When writing code for this project, you must adhere to the following architectural constraints:

- You are an expert in TypeScript, Lit, and modern CSS.
- Use standard Lit decorators (`@component`, `@property`, `@state`).
- Keep components small and reactive. Use Light DOM encapsulation (`createRenderRoot() { return this }`) to ensure seamless View Transitions and global themability.
- Do not use heavy frontend frameworks (React/Vue). Stick to standard web components.
- Write concise, performant code. Avoid over-engineering.
- For CSS, use standard nested CSS or modern native features (Container Queries, `color-mix`, native CSS variables).
- **Nested CSS:** All CSS rules MUST be nested to reflect the DOM hierarchy rather than using flat top-level class declarations.
- **Idiomatic HTML/CSS Naming:** Treat CSS class names as public APIs that could be externally themed. Avoid technical or structural terms like `btn`, `wrapper`, `container`, `layout`. Use concise, unified, and semantic idiomatic names that represent the domain (e.g., `.header`, `.entries`, `.time`, `.start`, `.end`, `.more`). Component templates should be as flat and simple as possible without redundant wrapper divs.
- When generating Calendar layouts, strictly use the CSS Grid approach.
- **Prefer CSS over JS:** If a layout can be solved with CSS Grid or Flexbox, do not use JavaScript math.
- **Calendar Grid:** The vertical time-grid uses `1440` rows. Map minutes directly to grid rows (e.g., 9:00 AM = row `540`).
- **Overlaps:** JS-based collision calculation is permitted *only* to assign `slot` and `total` overlaps. This data MUST be passed to the `<mitra-entry-segment>` instances strictly as CSS Custom Properties (e.g. `--overlap-slot`, `--overlap-total`), allowing CSS container queries to cleanly disable the clustering in narrow views (e.g., list views) without fighting JS logic.
- **Responsiveness:** Use CSS Container Queries (`@container`) instead of media queries. Components should adapt to their parent container's size, not the viewport.
- Strongly type all JSON API contracts from the backend proxies.
- **Dates and Times — two vocabularies, one boundary:** the FRONTEND (rendering, formatting, view math) uses `@3mo/date-time`'s `DateTime` global; SHARED/BACKEND domain code uses **Temporal types directly** (`Temporal.Instant` for absolute times, `Temporal.PlainDate` for calendar dates, `Temporal.ZonedDateTime` for wall-clock math — the full polyfill is injected into every bundle by `scripts/injectTemporalPolyfill.ts`, so shared code may use it freely). Never hand-roll zone/day arithmetic (Intl `formatToParts` loops, `± 86_400_000`, noon-UTC formatting tricks) — `shared/calendarDate.ts` holds the two date↔instant primitives, `calendarDateOf(instant, zone) → Temporal.PlainDate` and `midnightOf(plainDate, zone) → Date`, plus the named all-day API-boundary pair `normalizeAllDay`/`projectAllDay` built on them; date math beyond that is `PlainDate` instance methods (`since`, `subtract`, `equals`, `toLocaleString`). **Never spread a `PlainDate`** — its fields are prototype getters and spread to `{}`. `ICAL.Time` stays strictly at the .ics parse/serialize boundary (converted immediately via `CalDAV.instantFrom`/`toICALTime`); zoned .ics WRITES keep the resource's own VTIMEZONE (TZIDs aren't guaranteed IANA — Outlook writes `W. Europe Standard Time`). Avoid raw `Date` beyond storage/interop signatures.
- **2D Scroll Architecture:** Use a single scrolling container (`overflow: auto`) for the calendar viewport. Achieve 2D locked headers via `position: sticky` (`top: 0` for day headers, `left: 0` for the time axis, and `top: 0; left: 0;` for the top-left corner). Do NOT sync separate X and Y scroll containers with JavaScript.
- **Dynamic Minute Sizing:** To avoid browser sub-pixel layout limits (like `1fr` flooring at 1px), enforce the vertical 1440-row grid to fit its container using dynamic percentages (`--minute-height: calc(100% / 1440)` on a `height: 100%` grid).
- **Entry Clustering (Interval Graphs):** When resolving parallel entries, use strict Interval Graph Coloring logic to segment clusters completely before calculating columns and spans. This prevents disjoint entries from falsely grouping via distant shared neighbors.
- **Cross-Day Entries:** Do NOT attempt to span a single DOM element across multiple days. Split entries crossing midnight at the data/selector layer (e.g., `getEntriesForDay`). Pass the *original unmodified time range* to the UI component for accurate text display, but use boolean flags (`continuesNext`, `continuedFromPrevious`) to mathematically clamp the grid rendering between rows `1` and `1441` and to strip border radii visually.
- **Layered domain/view separation:** `shared/` holds *persistence/domain records only* (`Entry`, `Source`, `Integration`/`CalDAV`) + API models — no view concerns (do NOT put a calendar `laneRank` on `Entry`). An entity *may* expose facts about its own persistence, though — e.g. `Entry.persisted` (has the backend assigned it an id yet) is domain state, not layout. Calendar layout is a **frontend** concern: `EntrySegment` (in `frontend/`, not `shared/`) is one entry projected onto a single day and owns its per-day geometry, all derived from `(entry, date, previous/next links)`. The `EntrySegments` cohort owns every *cross-segment* computation. Keep this math out of the rendering components — `mitra-entry-segment`/`mitra-entry-details` are "decorations" that only read their segment for content/colour/identity while the view sets placement inline.
- **DateTime Operations:** Avoid raw `valueOf()` date math or manual year/month comparisons. Always use the native `@3mo/date-time` `DateTime` instance methods (`.equals()`, `.isBefore()`, `.isAfter()`, `.dayStart`) for bounding checks and equality. Rely on `DateTime.format()` to render strings so time values naturally inherit the system locale (e.g. Persian numerals).
- **RTL / Localization Support:** Always utilize CSS Logical Properties (e.g., `margin-inline-start`, `inset-inline-start`, `border-end-start-radius`, `padding-inline-end`) instead of physical directional properties (`margin-left`, `left`, `border-bottom-left-radius`) to ensure the application natively works in both LTR and RTL layouts. Avoid using `box-shadow` for asymmetrical borders (use pseudo-elements instead).
- **CSS Nesting / Shadow DOM Constraints:** Rather than fighting `:host([attr]) .child` selector specificity issues, attach boolean data attributes directly to structural markup (`<div ?data-state>`) and leverage native CSS nesting (`.child { &[data-state] { ... } }`).
- **Lit CSS Workaround:** Place all CSS directly within `static override get styles() { return css\`...\` }` rather than using `<style>` tags in the template. Use `import { css } from 'lit'` if `@a11d/lit` does not export it.
- **Scalable CSS Units:** Use `rem` instead of `px` values for most layouts (padding, margin, font-size, widths) to ensure responsive geometry. `px` should generally only be reserved for absolute rendering rules (like 1px borders or `@container` query thresholds).
- **CSS Variable Fallbacks:** Never hardcode default fallback values for theme variables (e.g., use `var(--color-background)` instead of `var(--color-background, #191919)`) since theme variables are guaranteed to exist globally.
- **A popover becomes a draggable bottom sheet by ANCHORING FALLBACK, not by a mobile breakpoint** (`components/sheet.ts`, `sheetStyles` + `initializeSheetGestures`). Opting in is two lines: `data-sheet` on the popover and `--sheet` appended as the **LAST** entry of its `position-try-fallbacks`. `@position-try --sheet` pins the popover to every viewport edge, so it can never overflow and the browser resorts to it exactly when every anchored placement failed — which is what "mobile" *means* for a fixed-width popover, and covers a squeezed desktop window for free. Descendants then restyle via `@container anchored(fallback: --sheet)` (Chrome 143+), so the whole mode switch is CSS. Consequences:
  - **The contract is ONE child carrying ALL the chrome.** In sheet mode the popover itself becomes a transparent full-viewport **scroll track** (its `::before` is a `100dvb` spacer whose start edge is the "closed" snap stop), so surface/border/radius/shadow must live on the single child in *every* mode — `mitra-entry-details` moved them onto its `> ul`, which also fixed the anchored mode (long content no longer scrolls the border away). The shared grab handle is that child's `::before`, so a sheet body must leave it free.
  - **Dragging is native scrolling, deliberately.** Snap stops (`block mandatory`) are the detents, so the finger is tracked by the compositor with the platform's own fling physics and release snaps to the nearer stop — there is no gesture code and must not be. **Never animate a non-composited property on the track itself**: an earlier dim as the track's own animated `background-color` forced a main-thread paint per frame and the sheet stopped following the finger, jumping straight to a stop. The dim is therefore a viewport-`fixed` `::after` animating **opacity** on a named `scroll-timeline`, which also makes it a box the mode switch creates and destroys — an anchored popover's track has no scroll range, so its timeline is inactive and Chromium paints the last value it computed (fill mode is irrelevant), which left a widened window's popover darkened behind its glass.
  - **Only two intents need script**, delegated once app-wide from `Mitra.initialized()`: `scrollend` at offset 0 dismisses (keyed on the rested offset, since the pseudo-element spacer can only report its originating element, making `scrollsnapchange`'s target an inference), and a press-then-click on the track dismisses (the track covers the viewport, so the platform's light dismiss can never see an "outside" click). Two guards are load-bearing, both learned by breaking it: the `scrollend` test **must** also require a non-zero scroll range, or anything that collapses the track (the fallback flipping back on a widened window, rotation) reads as a swipe-to-close and dismisses an editor the user never touched; and the tap-dismiss **must** require the POINTERDOWN to have landed on the track, not merely the click — the tap that opens an entry is still in flight when the sheet appears, and its trailing click is delivered to the by-then-full-viewport track, so keying on the click alone dismissed every sheet the instant it opened. That is the same click-versus-light-dismiss race `EntryDetailsComponent`'s rAF deferral documents, arriving from the other side.
  - **Closing slides out by scrolling too — `closeSheet(popover)`.** It runs the entry motion backwards (body down, dim fading with it) and lets the settle-at-closed dismiss path do the actual hiding; it returns `false` for a non-sheet, so callers fall back to `hidePopover()` (`EntryDetailsComponent.handleClose` does exactly this, keeping the anchored popover closing flat). Scroll-first-hide-second is forced by the platform: a popover cannot animate out once hidden, `beforetoggle` is cancelable for opening but **NOT for closing** (verified — `preventDefault()` is ignored), so a close cannot be deferred; and the standard exit route (`transition-behavior: allow-discrete` over `display`/`overlay`) is defeated regardless, because the editor leaves the DOM as soon as its `open` flips, cutting any transition off. Keeping the popover *open* for the length of the slide sidesteps both, and a grab mid-slide takes the sheet back for free. Escape needs the KEYDOWN intercepted for the same non-cancelable reason. Reduced motion needs no special case anywhere — `scroll-behavior` is already gated, so every one of these becomes an instant jump. **Delete is deliberately left abrupt**: the store removes the entry optimistically, so the segment and its popover are gone before a slide could finish.
  - **A popover host must be `display: none` while closed — never `contents`.** An author `display` beats the UA's `[popover]:not(:popover-open) { display: none }` however weak the selector, and because `EntryDetailsComponent` defers `showPopover()` by a frame, the element is in the DOM *and closed* for one frame on every open. `display: contents` generates no box for the host but still lays its CHILD out in the page flow — invisible while the host carried the visuals, but once the sheet contract moved surface/radius/shadow onto that child it flashed a stray glass panel into the calendar on every open (and let stray clicks hit fields inside the not-yet-shown editor, which spuriously opened its ⋯ menu).
  - **Verify sheets with real input events.** Opening via `segment.open = true` in a test harness bypasses the trailing-click race above, so it reported a perfectly working sheet while a real tap could not open one at all. Drive taps/clicks through the input layer (CDP `Input.dispatchTouchEvent`/`dispatchMouseEvent`), and wait for the previous editor to leave the DOM before tapping again.
  - **`position-try-order: most-block-size` is incompatible** and was removed from `mitra-entry-details`: ordered by block size the viewport-tall sheet sorts to the front and wins everywhere.
  - **Opening slides up because it SCROLLS, and it cannot be done any other way.** The track rests at its closed stop and the gesture module assigns the open offset, which `scroll-behavior: smooth` (in a `prefers-reduced-motion: no-preference` block, per the dialogs' convention) turns into the slide — so entry and drag are one motion through one mechanism, and the scroll-driven dim fades in with it for free. Both conventional approaches are *structurally impossible* here, each verified: (a) **`@starting-style` + transition cannot fire**, because it only applies at an element's first render and at that moment the popover has not been shown, so there is no anchor positioning, no resolved fallback, and the `anchored()` query does not yet match — by the time it does, a frame later, the window has closed; (b) **a transform cannot slide the body**, because the body is a snap target of a mandatory-snap track, so translating it moves its own snap area and the scroller re-snaps to follow, cancelling the motion exactly (the transform computes to a real matrix while the body's viewport position never moves a pixel).
  - **The rungs BEFORE the sheet matter as much as the sheet itself.** A multi-day all-day bar can span the whole week, so a ladder of only side placements (`inline-end` + `flip-inline`) falls through to the sheet on a full-size desktop — hence `mitra-entry-details` also tries below/above the anchor (`--below`/`--above`). Two constraints shaped those rungs, both verified: (a) they are **inset-based (`anchor()` + `justify-self: anchor-center`), not `position-area: block-end span-all`** — the position-area grid tracks follow the ANCHOR, and the week strip keeps buffer days in the DOM, so a wide segment's grid (and the containing block fallbacks are overflow-tested against) reaches past the viewport and the popover gets parked partly off-screen; zero inline insets pin the containing block to the real viewport, and anchor-center then shifts as far as needed to stay inside it. (b) They are **listed only at `width >= 40rem`** — on a phone they would often *fit* (any entry with room under it), and every placement that fits wins over the sheet, so an ungated list turns sheet-on-mobile into a popover lottery decided by scroll position. The sheet itself stays fallback-triggered, not breakpointed: a desktop window squeezed too tight for every rung still gets it, where the sheet body caps at `30rem` and centres (a bottom card, not a viewport-wide banner).
  - **Not yet opted in:** the popovers *nested* inside the entry editor (source `::picker(select)`, time-zone picker, repeat/reminder presets, location suggestions, the ⋯ menus). They keep their anchored placement at every width and measurably overflow a phone viewport — pre-existing, and the next step.
- **Backend ORM Strategy:** Exclusively use SQLite with MikroORM. Utilize Single Table Inheritance (`@entity({ discriminatorColumn: 'type' })`) for polymorphic domain models like `Integration` and `Entry` to allow simple querying of complex inherited data. A new STI subclass that adds no columns (e.g. a new `Integration` discriminator) needs no migration — just register it in `backend/ormConfig.ts`'s `entities` and `shared/index.ts`.
- **Database migrations (non-dev) vs schema sync (dev):** `backend/orm.ts` splits on `MITRA_DEV` — dev boots keep the `orm.schema.update()` diff-sync (branches/worktrees drift freely), every other boot applies the shipped migrations (`backend/migrations/migrate.ts` → `orm.migrator.up()`). **Any entity/schema change therefore needs a migration**: `npm run db:migration:create -- <PascalCaseName>` (name required, EF-style; emits `Migration<timestamp>_<Name>.ts` in repo style and auto-registers it in `backend/migrations/index.ts`), committed together with the regenerated `.schema-snapshot.json` (generation diffs the entities against the SNAPSHOT via an in-memory DB — never the local dev database). The backend bundles to one file, so migrations load via the explicitly imported `migrationsList` (index.ts's array order is authoritative — MikroORM doesn't sort it); never rely on on-disk discovery, and never edit or delete a committed migration — write a new one. Runtime config keeps `migrations.snapshot: false` (the migrator would otherwise write a snapshot file next to the production database). A database with entity tables but no `mikro_orm_migrations` log — any instance predating the mechanism — is **baselined** on its first non-dev boot: the initial migration is recorded as applied without running (it IS the last pre-migrations schema), and every migration after it **replays for real** — that replay is what carries DATA transformations (e.g. the source-type merge) that a wholesale schema sync would silently skip, so don't write ad-hoc upgrade/backfill code. Only a schema too old for the replay falls back to one `schema.update()` with everything marked executed (a loud warning tells the operator to re-import affected integrations); a migration failure on an already-migrated instance always propagates — never papered over. Because of this replay, a data-bearing migration must tolerate a database born on the CURRENT entities (a dev `schema.update()` build gets baselined too): introspect first (`pragma_table_info`) and no-op when the old shape isn't there. `db:migration:up`/`down` exercise the exact production path against `data/database.sqlite`. The ORM options live in `backend/ormConfig.ts` so the migrations CLI shares them without booting the app — which is why modules the config imports (entities like `State`) must never import `orm.ts` at module level (`State.read`/`State.write` take an `EntityManager` for exactly this reason).
- **SQLite table rebuilds in migrations must route through an FK-free holding table.** Migrations run inside a transaction, where `pragma foreign_keys = off` is a **no-op** — and with foreign keys enforced, `drop table` performs an implicit `DELETE FROM` whose `on delete cascade`/`set null` actions fire for real. The generated drop-and-recreate scaffold (`db:migration:create`'s `__temp_alter` pattern) therefore NUKES child rows when the rebuilt table is a parent: dropping `source` deleted every `entry` and nulled every `user.default_source_id` (caught by a fixture test — always test rebuild migrations with live child rows). The safe shape, see `Migration…_MergeSourceTypes`: park children's rows in a constraint-free holding table and drop the child table first, drop the parent only once nothing references it, recreate final shapes last — and capture/restore values that `set null` FKs would lose (`user.default_source_id`), re-pointing them when their target row was merged away. Sequential `await this.execute(...)` throughout (never `addSql`, which queues until after `up()` returns and can't interleave with analysis reads).
- **Entry type conversion = re-creation, never an in-place write.** An entry on a source that holds both types (see `Source.entryTypes`) may switch event ⇄ task at any time — draft or saved — via the editor's header switch. On CalDAV a task is a VTODO and an event a VEVENT with no mixing inside one resource (RFC 4791 §4.1), so the PUT route treats a type change exactly like a between-sources migration: re-create first, delete after, compensation on failure, new id adopted by the store from the response. The `status` field in the route's `incoming` literal is gated on the INCOMING type (the `Entry` constructor assigns in literal order, so an ungated later `status` would resurrect what the conversion dropped). A series is rejected (400) and the editor hides the switch for it — occurrence routing doesn't compose with re-creation.

It backs the dev sample data (`seedDev`) and lives in `backend/` (the frontend treats a `dev`-type integration as a generic one).

- **Notion = database VIEWS as task sources, token auth, own engine** (`shared/Notion.ts` + `shared/NotionClient.ts`, `discriminatorValue: 'notion'`): a direct `Integration` subclass (no CalDAV — Notion is a JSON REST API, pinned `Notion-Version: 2026-03-11`). Auth is a pasted internal-connection/PAT token (zero deployment config; the `(userId, uri)` identity is the token's bot user id, resolved as a `fetchSources` side effect via `GET /users/me`, which also yields the workspace label as `credentials.username`; `toJSON` masks the token like Google's grant). Sources are `notion://{dataSourceId}/{viewId}` — only databases with a **status AND a date** property qualify; Notion evaluates view filters server-side, so a source's membership is `POST /views/{id}/queries` (partial page refs). `NotionClient.views()` lists a data source's views (partial refs, no type) then GETs each for its name/type — and a view whose type the API refuses to serialize (`400 validation_error: Unsupported view type: feed`, and any future kind) is DROPPED, not fatal: one unsupported view must not abort discovery/sync for the whole account (a real "cannot connect Notion at all" regression when a user adds a feed view). Sync is **full-membership + incremental content**: deletions are the membership set difference (guarded: skipped when the membership is truncated at the 10k cap, and rows edited <2min ago are never removed — view indexing lag would otherwise eat just-created pages), content comes from ONE data-source delta query (`last_edited_time on_or_after` watermark−2min overlap, ascending sort so a truncation keeps the watermark behind the dropped edits); `changed` is decided by **field comparison** (`editEquals`), not the minute-rounded edit stamp. What Notion can't hold is DECLARED, not approximated: `Integration.capabilities` (base: all true; Notion: no recurrence/reminders/location/cancelledStatus/**timeZone**) drives the editor to HIDE those fields (`getCapabilities` in `Api.ts`, all-true fallback for plain-DTO providers like Dev), and the write mapping throws on recurrence/cancelled as defense in depth. **`description` IS supported: the page BODY ↔ markdown** via `shared/NotionMarkdown.ts` (uses the same `marked` the frontend renders with — now a `src/shared` dependency — so the editor's preview dialect is exactly what Notion receives, incl. `> [!type]` callouts ↔ callout blocks by color). The invariant both directions uphold: *a description edit replaces exactly what the description shows* — `toMarkdown` renders only blocks that are wholly re-authorable (`isReplaceable`, recursive: a bullet hiding an embed is opaque wholesale, as is any block whose children weren't fetched), the write pass (`Notion.replaceBody`) deletes only those (block DELETE = trash, recoverable) and appends the new blocks after the preserved rest, so images (Notion file urls expire hourly), embeds, sub-pages and synced blocks stay invisible AND untouched. The body reader (`fetchBodyBlocks`) descends only into `containerTypes` and exactly `maxNestingDepth`(=2) levels — the same cap Notion puts on write-payload nesting (deeper markdown lists flatten to depth-2 siblings), keeping read and write symmetric. Sync fetches the body for every page the delta serves (a body-only edit within the stamp's minute-rounding must never become permanently skippable, same reasoning as the property apply); a description-only local edit writes blocks then GETs the page for the fresh-stamp echo (no property PATCH), and the stored description is always the write's own normalized markdown (`toMarkdown(toBlocks(input))`) so the next sync compares equal and stays silent. `timeZone: false` because Notion's date property **cannot store a named IANA zone**: the API resolves any `time_zone` you send to a fixed offset and returns `time_zone: null` (verified against a real workspace — a `time_zone` sent with a `Z`/offset start even re-labels the wall clock, corrupting the instant, so `dateFrom` only ever pairs `time_zone` with a naive wall-clock, which preserves the instant). So Notion timed entries always read back `timeZone: null`, no per-entry authoring zone exists, and the zone picker / primary↔entry lens (`EntryDetailsWhen`) is hidden for them — the times still display in the viewer's zone (a view concern, unaffected). Status maps option→group via the data-source schema (page values carry no group); writes send each group's FIRST option id and only DIFFED properties (an unchanged Done never renames a "Shipped" option). A CREATE (and a migration, which routes through `createEntry`) pre-fills the view's own filter properties via `Notion.deriveFilterDefaults(view, dataSource)` — a page is created in the DATA SOURCE, not the view, so without this a task made in a filtered view (e.g. Area=University) never matches the filter and never appears. It reads BOTH `view.filter` AND `view.quick_filters` — real task views keep their filtering in the latter (`filter` is frequently `null`), keyed by RAW property ids while the schema url-encodes them, so `resolve` matches id / url-decoded-id / name. Only conditions a single value satisfies are honoured: select/multi-select/checkbox equality, status equality when the value is a real option (options can't be created on a page write, and the value may be a GROUP name), and **relation `contains <page-id>`** (the actual "Area = University" shape — set the relation to that page). OR branches, `does_not_equal`, formulas, date ranges, and filters on properties that don't resolve are skipped. mitra's own mapped fields always override a filter default (the user's chosen status is never rewritten to satisfy the view). A relation filter only resolves when the RELATED database is also shared with the connection — if it isn't, Notion omits the relation property from the schema/query entirely (it looks deleted), so mitra can't set it; sharing that database is the fix, not code. **The source strictly mirrors the view: there is deliberately NO local retention of a created task that doesn't match** (an earlier `createdHere` pin was removed at the user's request — "all should come from Notion"). A created task appears in the view iff its pre-filled properties satisfy the filter; if the view filters on something no value can set (a pure formula), the task lives in the database but not that view, exactly as in Notion. The deletion pass keeps only two guards, neither of which retains non-Notion content: skip when membership is truncated (10k cap), and a uniform short `localWriteAt` grace window (our own clock) so a brand-new legitimate member isn't deleted-then-re-added while Notion's view index catches up. `applyAndSync` (base) now rejects duplicate `(userId, uri)` connects with a clear error before flush. The add dialog pre-selects only ONE view per database (overlapping views would render a task once per view — a documented, deliberate user choice).
- **Sync pacing lives on the integration, presence decides the cadence**: `Integration.syncInterval` (ms, default 0 = every cycle, **`Infinity` = local-only, never polled** — `Dev` today, an Obsidian-style provider tomorrow; skipped by background AND manual sync) lets rate-limited providers poll politely — `GoogleCalendar` and `Notion` return 60s. That pacing IS the quota protection (Google's CalDAV shares the Calendar API limits: 600 req/min/user, 1M req/day/project; an idle sync is ~9 requests, so 60s ≈ 13k/day per account — the DAILY project quota binds first). The decision core is **`SyncPacer`** (`backend/SyncPacer.ts`, pure + unit-tested): per integration, the largest of three floors wins — the presence cadence (**10s while the owner has a connected client, 5min otherwise**; `backend/presence.ts` counts open `/api/events` streams per user), the provider's `syncInterval`, and a **flat** 60s failure rest (deliberately not exponential: at these volumes extra backoff buys no protection, and flat keeps recovery within a minute of the server coming back). The `Synchronizer` is orchestration only: a 10s heartbeat re-evaluates due-ness (the RESOLUTION, not a poll rate), every cycle (heartbeat / reconnect / manual) is serialized through one queue, and each integration syncs in its own try/catch (one broken account doesn't block the rest). **A user coming online triggers an immediate cycle for them** (presence `onOnline` → user-scoped sync) — that's what makes a page reload/laptop-wake show fresh data with zero frontend code. **There is deliberately NO manual "sync now" — no endpoint, no button, no palette command** (the user's call): a refresh affordance implies the calendar on screen might be stale, and reloading the page is the gesture users already reach for — presence turns it into a sync for free. Even a presence-triggered cycle respects the pacer, so reload-spamming can't hammer a provider. Pace transitions log at **debug** (`came online — syncing now…` / `went offline — polling relaxes…`) via `presence.onOnline`/`onOffline`. Pacer state is in-memory on purpose: a restart retries everything, the right recovery.
- **"Sync" and "re-import" are two different operations and never share a word** (renamed from `resync*`, which read as "sync again" — exactly what a plain sync already is). **Sync** = the incremental background pull (`Integration.sync`/`syncEntries`/`syncSourceEntries`, `syncInterval`, `Source.syncState`, the `Synchronizer`); it has no client trigger at all. **Re-import** = the wipe-and-rebuild recovery hatch (`Integration.reimportSource`, `POST /api/sources/:id/reimport`, `POST /api/integrations/:id/reimport`, `Api.reimportSource`/`reimportIntegration`, the sidebar's "Re-import entries" with the `hard-drive-download` icon — never `refresh-cw`, which would read as a sync). Keep the split in code, routes, UI labels, and docs; `t('Refresh')` survives only in the connect dialog, where it re-discovers an account's SOURCE LIST (a third, setup-time action).
- **The integration dialog is two-step on add, and provider-agnostic via polymorphism, not `instanceof`**: the add flow first picks a type from a tile grid, then shows that type's details panel. The tiles are built from the shared registry (`integrationClasses()` — every `@integration`-registered subclass, in registration = display order), NOT a list in the dialog: each connectable class OWNS its own presentation as statics — `label`, `logo` (an asset key), `description` (English source text) — so a provider's identity lives in one place, its class. The entity is constructed ONCE with its final class (`new integrationClass(...)`); there is no in-place type conversion — going back to the picker discards the entity (and any in-flight discovery result, guarded by entity identity). Editing skips the picker entirely: `Integration.editableCopy()` (the mirror of `merge`) hands the form a transient same-class copy — identity + uri kept, `editableCredentials` blanked per provider (CalDAV blanks the password, Google the grant), sources as a plain array (JSON-serializable — a live Collection holds a circular owner reference). The dialog derives its details panel from the `type` discriminator, defaulting to the CalDAV panel for provider types the client doesn't model (e.g. Dev). **Adding a provider = a new `@integration` subclass (with its statics + a `logo`/`canConnect`) + its SVG asset + one panel case + one logo-map entry** — no edits to a central list. NB: the `@model` registrations the API reviver needs survive via `shared/index.ts`'s `export *` because decorator application is a side effect — don't convert those exports to type-only.
- **A provider's identity, presentation, and connect-preconditions live on its class — kept plain so shared/backend stay clean.** These domain classes double as the frontend's API models, so their presentation statics are **plain data only**: `label`/`description` are strings (no `t()` — that global is frontend-only and would break the backend; the dialog localizes `description` at render, and `scripts/i18n.ts` scans the `description` statics so those keys stay tracked), and `logo` is an asset KEY, never a lit template — the SVGs live in `assets/integrations/*.svg`, import as text (esbuild's `.svg` `text` loader, frontend only), and render inline via `unsafeHTML` so the monochrome marks inherit `currentColor` (Google keeps its own gradient). Whether a connection can be attempted is domain knowledge too: `Integration.canConnect` (base: server URL + username; Apple: username only, its URL is fixed; Notion: token only) gates the dialog's Connect button — the dialog adds just the edit policy (an edit always refreshes, the server holds the stored secrets).
- **A fresh `Integration` knows its own `type`**: the `@integration(type)` decorator stamps a `type` static on the class (also its map key) and the base constructor reads `new.target.type` to set the STI discriminator (MikroORM only back-populates `type` on load). ONE `Map<type, class>` (`registeredIntegrations`) serves everything — `integrationClassFor`'s API/backend dispatch, the dialog's `integrationClasses()` tiles, and the self-stamp. So a freshly constructed instance serializes its `type` on the wire and nothing sets it by hand; unregistered internal-only subclasses (Dev) have no `type` static, stay unstamped, and get their discriminator from the ORM on persist.
- **Incoming request bodies are PLAIN DTOs, not rehydrated entities.** `@a11d/api` `structuredClone`s the body before sending, which strips the prototype — so `@type` (a prototype prop set by `shared/model.ts`), `toJSON`, and every **getter** are gone on the wire, and the server's `express.json` reviver never reconstructs request-body models. Backend code reading a request body must touch only **plain data fields** — never call a method/getter on it or rely on `instanceof`. This bit source enabling: `Integration.applyAndSync` keyed `incoming.sources` via the `Source.key` **getter** (→ `undefined` on a plain object → every source disabled). Fixed with the static `Source.keyOf({type, uri})` (the getter delegates to it) for the incoming side. Key/compare incoming-body fields by hand, not via a getter.
- **All-day:** `Entry.allDay` is a **persisted flag**, not inferred from midnight times. CalDAV reads it from a date-only `DTSTART` (`event.startDate.isDate`) on sync and writes `DTSTART;VALUE=DATE`/`DTEND;VALUE=DATE` (exclusive next day) on create/update; `start`/`end` still carry the day bounds (midnight → exclusive next midnight) for rendering. Always set the flag where an entry is created (drag, seed, sync).
- **All-day bounds are calendar DATES, not instants** (`shared/calendarDate.ts`): stored canonically as **UTC midnights**, which is zone-less and deterministic — the deployment container's TZ is irrelevant. They cross the API in the VIEWER's zone: every entry read/write sends `?tz=<browser IANA zone>`; reads project the dates to the viewer's local midnights (`projectAllDay`, entries.ts `projectedForViewer`), writes normalize the viewer's midnights back to dates (`normalizeAllDay` — including scoped-edit/delete `recurrenceId`s, which round-trip through projected data). So an all-day event covers the same dates, midnight-to-midnight, in every browser zone. Rules that follow from this: NEVER `toJSDate()` a date-only ical.js value (server-local midnight — the prod overlap bug; use `CalDAV.instantFrom`, which reads y/m/d → UTC); all-day series expand/shift/exclude in **UTC** (`occurrences.ts dayMathZoneOf` — `entry.timeZone` governs only TIMED wall-clock math). **No data migration for pre-convention rows** (matching the OIDC precedent): rows written before this convention keep their old zone-shifted midnights — users **re-import** their integrations to re-canonicalise, so don't write backfill code. Known trade-off: all-day reminders anchor to UTC midnight (per-viewer reminder zones are a future concern).
- **Background Sync Architecture:** All data synchronization should occur entirely in a background daemon (e.g., `server.ts` loop) that polymorphically iterates over all base `Integration` records. Do NOT block frontend API reads with live external syncs; the frontend `/api` routes must always query instantly from the local SQLite store.
- **CalDAV Sync Quirks:** When syncing CalDAV via `tsdav`, **do not** use `smartCollectionSync` or `smartCollectionSyncDetailed`. It has a hardcoded bug that filters out any calendar URLs that do not end in `.ics`, breaking platforms like some CalDAV servers. Always implement manual WebDAV XML syncing by passing `client.syncCollection()` directly and fetching `changedUrls` manually.
- **Multiget must tolerate per-member 404s.** `client.fetchCalendarObjects({ objectUrls })` runs ONE `calendar-multiget` REPORT, and tsdav's `collectionQuery` **throws if ANY member response is ≥ 400**. Google (and any server) can report a member that vanished between the sync-collection listing and the fetch with a per-href 404 — on an incremental delta especially — which would otherwise abort the entire source sync. Worse, the abort happens before the caller flushes the advanced sync token, so the *same* delta is retried forever (a `reimportSource` that wipes the token dodges it — hence "reimport fixes it, save doesn't"). `CalDAV.fetchObjects` wraps the multiget: batch first (fast path, one request), and on throw refetch each object individually, dropping the gone ones so the sync completes and the token advances. Route the changed-object fetch through it, never `fetchCalendarObjects` directly.
- **Date writes preserve the resource's AUTHORED FORM** (`CalDAV.writeDate`): a `DTSTART`/`DTEND`/`DUE`/`EXDATE`/`RECURRENCE-ID` that carried a `TZID` is rewritten as that zone's WALL CLOCK (via the resource's own VTIMEZONE), keeping the parameter; zoneless values stay UTC (`toICALTime`), with any stale `TZID` parameter dropped. Never `updatePropertyWithValue(name, ICAL.Time.fromJSDate(date, true))` directly on an existing date property — ical.js keeps the old TZID parameter, the zone reinterprets the UTC wall clock, and the event shifts by the zone offset on zoned servers (Google authors TZID forms; a Berlin series moved to 10:00 landed at 08:00 local this way, and Google then detached its orphaned exception into a standalone event). A fresh `EXDATE`/`DTEND` follows DTSTART's form (RFC 5545 matches instances by it). Also: **a series-wide start shift shifts bundled override `RECURRENCE-ID`s** (components + local rows) by the same delta in `updateEntry` — an unshifted override orphans, and the expansion renders both the shifted occurrence and the exception. The overrides' own DTSTARTs stay (a custom-timed exception keeps its custom time).
- **Google bumps the etag AGAIN after accepting a write** (async normalization), so a second edit of the same resource within a sync cycle carries a stale If-Match and would 412 spuriously. Every CalDAV write therefore goes through **`CalDAV.writeResource(entry, applyTo)`**: the edit is a pure `raw → raw` transformation (`applyTo`), attempted with the stored etag and — on a 412 — re-applied ONCE onto the refetched current resource with its fresh etag (`refetchResource`). This keeps the guard's meaning: a genuine concurrent change simply becomes the base the field edit merges onto (the same semantics any edit has), and a second 412 propagates. `deleteEntry` retries its DELETE the same way (and treats a 404 as success — already gone). When adding a write path, express it as an `applyTo` closure (idempotent — it may run twice; anything non-idempotent like row mutations or delta computations stays OUTSIDE) and route it through `writeResource`, never `updateCalendarObject` directly.
- **Opt-in Data Flow:** Newly discovered external sources (like new calendars) should always be persisted to the DB with `enabled: false`. Do not perform heavy `Entry` syncing loops until the user explicitly enables a source.
- **Source reconciliation preserves LOCAL renames** (`Integration.getSources`): a user can rename a source (`PUT /sources/:id/name`), and a background sync must not reset it to the provider's name — the previous bug (`match.name = source.name` unconditionally, every cycle). `Source.remoteName` (nullable column, since folded into the initial migration) stores the provider's name as of the last reconcile. Reconcile rule: a **new** source records `remoteName = name`; a **matched** source with a `null` baseline (a row predating the column) records the provider name silently WITHOUT touching the displayed `name` (so an existing rename survives the first post-upgrade reconcile); otherwise the provider name is adopted only when it **changed** since last reconcile (a genuine REMOTE rename — a local custom name yields to it), and an unchanged provider name leaves the row's current name alone. Same pattern would apply to any per-source field a user can override locally (only `name` today; `color` is already write-once-then-user-owned).
- **Incoming request bodies are PLAIN DTOs, not rehydrated entities.** `@a11d/api` `structuredClone`s the body before sending, which strips the prototype — so `@type` (set by `shared/model.ts`), `toJSON`, and every **getter** are gone on the wire, and the server's `express.json` reviver never reconstructs request-body models. Backend code reading a request body must touch only **plain data fields** — never call a method/getter on it or rely on `instanceof`. This bit source enabling: `Integration.applyAndSync` keyed `incoming.sources` via the `Source.key` **getter** (→ `undefined` on a plain object → every source disabled on save). Fixed with the static `Source.keyOf({type, uri})` (the getter delegates to it) for the incoming side. Key/compare incoming-body fields by hand, not via a getter.
- **Living Architecture:** Whenever a new architectural decision is made by the user, **ALWAYS** add it to this `AGENTS.md` file immediately so that rules compound and the user doesn't have to repeat themselves.
- **Living Documentation:** User-facing operator docs live in `docs/` (plain Markdown with **Starlight-compatible frontmatter**: `title`/`description` + optional `sidebar.order`). Callouts use **GitHub-style alerts** (`> [!NOTE]`/`> [!TIP]`/`> [!CAUTION]`) — NOT Starlight `:::note` asides — and pages link each other with **relative `*.md` paths**; a folder's overview page is named **`README.md`** (so GitHub renders it when browsing that folder) — the folder is fully navigable on GitHub. The docs *site* is `website/` (Astro + Starlight, a standalone package outside the npm workspaces — excluded from root lint/Docker), deliberately minimal: `docs/` and the repo's single `assets/mitra.svg` are the only sources, wired in by `website/prepare.mjs` at pre-dev/build (a `src/content/docs` link — Starlight hardcodes that path — plus the git-ignored logo/favicon copies). The docs collection's `generateId` (in `content.config.ts`) treats `README.md` as a folder's index (root `docs/README.md` → `/`, `docs/integrations/README.md` → `/integrations/`). `astro.config.mjs` translates the GitHub alerts + relative `.md` links at build time (`remark-github-blockquote-alert` + an inlined base-aware rehype plugin), so content never needs site-specific syntax; build with `cd website && npm install && npm run build`. Deploy is `.github/workflows/docs.yml` → GitHub Pages, with the host/base passed as `MITRA_DOCS_SITE`/`MITRA_DOCS_BASE` env (moving hosts is a two-value change, nothing in the committed config assumes Pages). Whenever a change adds or alters anything an operator **configures or sees** — a `MITRA_*` environment variable, an integration/provider, a setup or deployment step, an operational surface like `/api/health`, or user-visible behaviour that needs explaining — you **MUST** update `docs/` in the same change. Any new or changed environment variable **must** be reflected in the reference table at `docs/reference/environment-variables.md`; a new integration needs a `docs/integrations/<provider>.md` page. **`docs/integrations/<provider>.md` carries only what is TRUE OF THAT PROVIDER** — its connection details, its server URLs, what its data model can and can't hold. Behaviour that works the same whichever account you connected (the sidebar's sources: importing, hiding, renaming, recolouring, reordering, the default source, re-import) belongs in ONE page under `docs/guides/`, which the provider pages then link — otherwise the first provider page to be written silently becomes the manual for the whole app (reordering was documented under CalDAV exactly that way). `docs/guides/` therefore holds two kinds of page, and `docs/README.md` groups them accordingly: **Use Mitra** (what a user does in the app — `calendars.md`, `keyboard-shortcuts.md`; `sidebar.order` 0…) and **Administer your instance** (deployment and operations — everything else). ## Multi-user & authentication (OIDC)

- **Zero-auth single-user is the default**: `authMiddleware` attaches the seeded `[default_local_user]` to every request. Setting `MITRA_OIDC_ISSUER` (+ `MITRA_OIDC_CLIENT_ID`, `MITRA_URL`, optional `MITRA_OIDC_CLIENT_SECRET`/`MITRA_OIDC_SCOPES`) switches on multi-user mode; a half-configured issuer fails the boot loudly (`Oidc.fromEnv`).
- **The BACKEND is the OIDC relying party** (`backend/Oidc.ts`, Authorization Code + PKCE via `openid-client`, routes under `/auth/*`) — deliberately NOT frontend `oidc-client-ts` + Bearer tokens: the SPA is same-origin (one Express serves both), `@a11d/api` already sends cookies, and tokens staying server-side beats XSS-exposed browser storage. Discovery is lazy and retried (the IdP may boot after mitra in the same compose stack); an `http:` issuer is allowed for LAN/compose-internal IdPs.
- **Sessions are mitra's own** (`backend/Session.ts`): an opaque 256-bit cookie token stored SHA-256-hashed as the row id, sliding 30-day expiry. The IdP's tokens are discarded after sign-in — mitra calls no upstream APIs for the user — except the raw `id_token`, kept per session as the `id_token_hint` for RP-initiated logout. CSRF rests on `SameSite=Lax`. Unauthenticated requests split by kind: `/api/*` → 401 (the frontend's `ApiError` bounces through `/auth/login`), asset paths (with an extension) pass — bundles and the PWA manifest are public code — and page navigations redirect to `/auth/login?returnTo=…`.
- **The OIDC identity is a value object, not flat columns**: `Identity` (`shared/Identity.ts`) holds `issuer`/`subject` (the key — a subject is unique only within its issuer) plus the vouched `email`/`name`/`picture` (the photo is stored as a LINK only — the browser loads it from the provider), embedded into `User` as `oidc_*` columns via `@embedded(() => Identity, { prefix: 'oidc_', nullable: true })` — the same MikroORM embeddable pattern as `Recurrence` on `Entry` (registered in `orm.ts` entities; unique on `['identity.issuer', 'identity.subject']`). Absent entirely in single-user mode, so `user.identity` presence IS the "is this an OIDC user" test (frontend + backend). Behavior lives on it: `Identity.fromClaims` / `applyClaims`.
- **JIT provisioning is domain behavior**: `User.provision(em, issuer, claims)` matches on the embedded `(issuer, subject)` and creates a fresh user on first sight. `email`/`name` refresh from the ID token on every sign-in. **No data migration**: enabling OIDC does NOT carry the single-user default user's data over — every identity (incl. the first) starts empty and re-adds its own integrations. This is a deliberate call (the user's): don't write upgrade/backfill code; tell users to reimport.
- **Ownership scoping lives on `User`**: routes resolve entities exclusively through `user.integrations/integration/sources/source/entry` — a foreign id throws `NotFoundError` → the central 404, never leaking another user's data. Never use a bare `em.find*` for user-owned entities in a route unless ownership was already proven upstream in that handler.
- **Everything user-adjacent is per-user**: `syncEmitter.emit('updated', userId)` (the SSE feed filters by `req.user.id`; `Synchronizer` collects changed owners per integration), push subscriptions carry a required `userId` set at subscribe time (re-registration on boot reassigns a shared browser to whoever is signed in) and reminders route via entry → source → integration → owner (`sendTo(userId, …)`).

## Calendar layout & segmentation (current model)

- **View components are named after the unit they strip**: `Days` (`mitra-days`) is the week view's horizontal strip of day columns; `Weeks` (`mitra-weeks`) is the month view's vertical strip of week rows. A future view follows the same scheme (e.g. a year view = a strip of months). The user-facing *view* names ("Week"/"Month") and the drag controller's `grid` discriminants stay as-is.
- **`EntrySegments` (frontend cohort) is the whole layout engine** — small, because CSS does the placing. Build via `EntrySegments.of(entries, days)` (memoised on `days`). API:
  - `EntrySegments.for(entry)` — the entry's per-day segments, linked `previous`/`next`, memoised so instances are stable across renders.
  - `timedOn(day)` — the day's timed segments clustered into side-by-side columns (the *one* genuinely cross-segment computation; writes each segment's `overlap = {slot,total,span}`).
  - `runsIn(from, to, accept)` — one representative segment per matching entry whose run touches the window, sorted so DOM (and paint) order stays deterministic. Used for the week all-day lane and per-week in month.
  - `monthSlots` / `allDaySlots` / `monthWeek(week, maxSlots)` — computed lane packing (one shared greedy `slots` pass). Month needs exact lanes for its "+N more" overflow; the week's all-day lane needs them for its explicit row tracks (`allDaySlots` packs only all-day entries — timed ones never hold a lane there). **A move's ghost is packed LAST, over the settled lanes:** it previews the lane the entry *lands* in (so the bar doesn't jump on release), with the cells its own drag SOURCE holds counted as free — they vacate on release, so a bar dragged along its own lane keeps it. It never shifts a real bar, never grows the all-day strip (a ghost that fits nowhere rides the trailing empty lane), and in the month grid it is never counted as "+N more" overflow — past the cap it rides the last visible slot, because the ghost is the drag's only feedback and may not vanish.
  - `static laneRank(entry)` — lane ordering for month packing (a view concern, hence here and not on `Entry`).
- **Grid gestures — one `EntryDragController`, both views, three gestures.** Attached to the grid *container* (`Days`/`Weeks`), never per-`Day`, so a gesture can span day cells; the view selects the surface with a `grid: 'week' | 'month'` arg. It snapshots cell geometry once at pointer-down (so each move is pure arithmetic — no per-frame reflow), coalesces moves to one update per animation frame, captures the pointer on the host, and tears down on pointerup **or pointercancel**. Pointer-down classifies the gesture once (a `kind` discriminant): a `.resize-start`/`.resize-end` handle → **resize**, a persisted entry's body → **move**, empty grid/lane/cell → **create**. It also **owns tap-to-open** (a no-move tap on a body opens the editor) — `mitra-entry-segment` has no click handler, so a drag can't fire a stray open on the wrong slice. Geometry/granularity are shared: timed only in the week's grid (minutes off the 1440-row grid, snapped to `snapMinutes`); the all-day lane and the *whole* month are day-granular (a timed entry moved in the month shifts whole days, keeping its clock time).
  - **create** — week timed/all-day lane/month, as before (plain click: nothing in week, quick-create a day in month). New entries target the dev sample calendar in development.
  - **move** — translate a persisted entry preserving duration (clone both ends by one delta; the result's leading edge snaps to grid). Allowed for every entry, including timed-in-month.
  - **resize** — drag one edge while the other stays fixed, reusing the create min/max-flip placement (`entryPlacement.ts`), so dragging an edge past the other flips gracefully and multi-day spans fall out for free. **Pure placement math lives in `entryPlacement.ts`** (`placeTimed`/`placeAllDay`/`resizePlacement`/`snapToGrid`) — dependency-free and unit-tested (the all-day exclusive-next-midnight bound makes the fixed *trailing* edge `end − 1 day`).
  - **Resize handles** are 0.25rem strips rendered by `mitra-entry-segment` per a `resize: 'block' | 'inline'` prop the view sets (Day timed → block/vertical, all-day lane + month all-day bars → inline/horizontal, **month timed bars → none**, gated on the entry's *persisted* `allDay` flag, not the segment's derived one). CSS hides a handle at a clipped/interior edge via the same `has-previous`/`has-next` attributes (so `MonthBar` exposes `clippedRight`) and drops block handles on too-short entries.
- **Drafts & optimism — one pending local entry, new *or* edited.** A locally-**created** entry (drag/click) has **no id** (the backend assigns one on create, so `Entry.persisted` = `id != null` *is* the draft test — no flag, no status enum). An **edit** (move/resize) is a *clone* of an existing entry with mutated start/end (same id) — never an in-place mutation, so a cancelled gesture leaves the original untouched. `DraftController` (static store) holds the one pending entry: `mergeInto` substitutes it over the server copy by id (an edit) or appends it (a not-yet-saved create); `reconcile` (called from the page's fetch) drops it once the server echoes the **matching content** (start/end/allDay) — id alone would drop an edit's overlay before its update lands and snap it back. **Commit:** create → `createEvent` (no id), set the returned id in place; move/resize → `updateEvent(clone)`, reverting *that* draft on failure. A `dragging` flag floats the actively-dragged entry above its cluster. Components attach an instance only to **subscribe**.
- **Backend owns ids:** `Entry.id` has no default; assign one at every persist site (the POST route — which covers both providers' `createEntry` — plus `seedDev` and CalDAV sync). The frontend never mints ids; a missing id means "not yet saved".
- **Hot-loop date math:** `@3mo/date-time` rebuilds a `Temporal.Instant` **and** `ZonedDateTime` on *every* accessor (`.hour`/`.dayStart`/`.equals`/`.isBefore`…), which dominates per-frame render/clustering loops. So compare **cached epoch-ms day numbers** instead: `EntrySegment` memoises its numeric projections (`startMinute`/`endMinute`/`dayValue`) and segments are globally memoised (`EntrySegments.for`), so the Temporal cost is paid once per segment; compare `dayValue`/`fallsOn(dayValue)` (or hoist a `dayStart.valueOf()` out of the loop) rather than `dayStart.equals(...)`. The richer `DateTime` comparison API still applies to non-hot code.
- **Self-placement:** views map a date → grid column themselves (build a `Map<dayValue, index>` once per render — never `findIndex` inside `.map()`) and set `grid-column`/`grid-row`/`--overlap-*` inline. The all-day lane self-places columns by date and rows from `allDaySlots`. `CalendarLayout` (an old shared class) was removed — don't reintroduce it.
- **The time axis' ALTERNATIVE zone columns fold; the anchor zone never does.** Every additional zone costs another sticky column the day tracks never get back, which a phone can't afford — so the week's zone lane collapses to just the zone the grid is built on. **One registered length is the whole mechanism**: `--zone-width` (`@property <length>`, `inherits: true`), so opening is a CSS *transition* on that one property and dragging is that same property driven per frame — **nothing about the grid is rebuilt in JS**. `[hideTime]` zeroes it too, so empty tracks reserve no width.
  - **It clamps the CELLS, never the tracks** — `max-inline-size: var(--zone-width)` (plus `box-sizing: border-box`, `overflow: clip`, and padding that folds with it) on the alternative zones' hour cells and header chips; the track list stays the plain `auto` one this view has always had. Both other levers were tried and are wrong: a **fixed track length** pads a short label ("IR") out to the full column width while the anchor's `auto` track hugs its content — visibly uneven columns — and **`fit-content(var(--zone-width))`** collapses the *open* track to its base size, because grid only grows a track toward its growth limit by distributing FREE space and the 1092-day buffer always overflows. Clamping the cell keeps the base size itself content-derived, which is the only reason `auto` tracks hug their content here (min-content == max-content for unbreakable `HH:MM` text). Corollaries: a definite `max-inline-size` clamps the min-content contribution too, which is what lets `auto` follow the fold to zero; `min-inline-size: 0` would *break* it (it waives the very minimum the track is sized from); and `overflow: clip` does NOT zero a box's automatic minimum size the way `overflow: hidden` does — it establishes no scroll container. `--zone-lane-width` is therefore a **ceiling**, not a width: it only has to clear the widest compact label a zone can carry (Intl's `GMT+3:30` ≈ 62px, hence `4rem`), and it doubles as the drag's clamp. The fade uses the same length ratio as the day-fit math (`clamp(0, tan(atan2(var(--zone-width), var(--zone-lane-width))), 1)`), hence both operands are registered.
  - **`TimeZoneLaneController` owns the STATE, the stylesheet owns the BREAKPOINT.** A deliberate fold is remembered per browser (`Mitra.TimeZones.Folded`, absent = no preference); until there is one, a container query (`@container (max-width: 40rem)`) writes its verdict into `--_auto-fold` and the controller reads it back — the threshold is never duplicated in JS. That verdict only exists after layout, so it's read in `hostUpdated` (once; later changes arrive via a ResizeObserver) **behind a `[data-zones-immediate]` no-transition attribute with a forced style flush** — otherwise a narrow viewport paints the lane open and animates it shut on every load.
  - **Gestures**: an inline drag on the rail (`.timezone, .axis` — `touch-action: pan-y` there, but only while there IS a lane to fold, so a bare axis keeps panning the strip) moves the lane 1:1 with the pointer (each column takes an n-th of the travel), claimed only past 8px and only when `|dx| > |dy|`; releasing past halfway commits. Touch, pen and mouse take the identical path. Haptics go through `frontend/haptics.ts` (`haptic(ms)` — the user-activation + missing-API guards in one place, shared with `EntryDragController`): a light tick when the drag crosses the point of no return, a fuller pulse when it lands.
  - **The chevron button costs the axis NOTHING** (the user's explicit call): it is absolutely positioned under the "+" in the empty all-day corner, not a second in-flow item in the leading track — that track is sticky chrome, so an extra icon would take that width off the day columns forever, in the very state (unfolded) where a fold button matters least. Revealed by hover/`:focus-within` alongside the "+", with `pointer-events` following the reveal (an invisible toggle over the corner would swallow grid clicks) and a flush `padding-block-start` so travelling down to it never leaves the header and blinks the reveal off. **Touch deliberately gets no button** — the rail drag is the affordance there. Adding a zone auto-reveals the lane (`fold` dispatches a target state, not a toggle), so a new column is never created invisibly; a folded alternative chip drops out of the tab order and stops answering the pointer.
- **The week all-day lane has EXPLICIT row tracks, never auto-flow rows behind a `min-block-size`.** The view computes the window's lane count over the REAL bars (`allDaySlots`, +1 trailing empty lane as the drag-to-create target) into `--_all-day-rows`, and renders a per-day `.day` surface cell spanning `grid-row: 1 / -1` so the day columns' colour and 1px separators continue through the strip. Why not `grid-auto-flow: row dense` + `min-block-size` (the old model): the timed row is measured to fill the viewport exactly, so `mitra-days` never has free space and the lane's `auto` row sits at its *base* size — and a specified min-size REPLACES the content-derived minimum there, freezing the lane at the min while extra bars overflow onto the timed grid. Beyond `Days.MAX_VISIBLE_LANES` (4) the strip stops growing and scrolls within itself (`[data-all-day-overflow]`, attribute-gated because a scroll container would capture the bar titles' inline stickiness even when nothing overflows).

- **Scroll snapping is gated on the SCROLL DEVICE, and the line is notched-vs-continuous.** `Days` and `Weeks` keep `scroll-snap-type: … mandatory` unconditionally; what switches is `scroll-snap-align` on their snap *targets* (a container with no aligned targets has no snap positions — that is how "don't snap" is expressed without touching any other scrolling property). A trackpad, finger and pen all snap; a notched wheel and middle-click autoscroll do not, because a snap position between two discrete notches brakes every one of them. No media query can decide this: `pointer`/`any-pointer` describe the *hardware* statically, and a wheel and a trackpad are the same device to every one of them. So `ScrollDeviceController` (on the application root, `@eventListener` on `window`, capturing + passive) stamps `data-scroll-device`, and its own `static styles` translates that into `--scroll-snap-align` — a custom property because the views reading it are in shadow roots, same mechanism and reason as `focusRing.css.ts`. **No `@media (pointer: coarse)` seed**: nothing snaps until a device identifies itself, and a finger fires `pointerdown` the instant it lands, long before the pan it starts can settle. Wheel-vs-trackpad is a documented heuristic (legacy `wheelDelta` quantised to 120, or a non-pixel `deltaMode`) with one inherent false positive: a trackpad fling landing exactly on a multiple.

## Yearly view (the months strip)

- **`mitra-months` (frontend/Months.ts) is the year view — and it's a strip, not a "year"**: the vertical sibling of `Days`. One row per month scrolling seamlessly across year boundaries on the same `CalendarDatesController` 3-year buffer (`radiusDays: 240`), one column per weekday-aligned day slot (`31 + daysInWeek - 1` = 37), so weekdays line up vertically across the whole year like a paper wall planner. "Year" is just this strip at its default density (12 rows fill the viewport); custom spans (quarters, "X months") are density presets, not new components.
- **Cells are `mitra-day`, not bespoke divs** — the day component's own container queries carry it down to year scale: a new compact tier (`@container ((max-height: 8rem) or (max-width: 3rem))`, unreachable by the month's ≥8.5rem cells and the week's ≥10rem columns) collapses the header to a bare centred numeral and hides the weekday/month parts. Extend `mitra-day`'s versatility for a new scale; never fork a parallel cell.
- **Month grouping lives on `CalendarDatesController`** (`get months(): CalendarMonth[]`) — deriving calendar structure from the buffer is the controller's job, not a view's. `CalendarMonth` is a thin **value object** over the month's consecutive days (`number`/`firstColumn`/`columnOf`/`intersects`), computed on read with **no cache**: `@3mo/date-time`'s `DateTime` memoises every accessor per instance (`zonedDateTime`/`dayStart`/`month`/…) and the buffer's day instances are stable across renders, so the grouping is cheap plain-array work and precomputing/caching day-start keys buys nothing. Buffer days carry the buffer's *generation clock time*, so `firstValue`/`lastValue` and `data-date` still go through `.dayStart`.
- **Lanes are pure CSS, overflow clips**: bars render into a per-month `.entries` overlay (subgrid columns, `grid-auto-rows: 1rem`, `grid-auto-flow: row dense`, `pointer-events: none` with interactive bars) — like the week's all-day lane, no JS lanes and no "+N more". DOM order is the packing priority: a stable sort by `EntrySegments.laneRank` (multi-day arcs → all-day → timed) so the entries that shape a year keep the visible lanes; a too-dense row clips under a bottom fade mask, and zooming in is the reveal. The segments' own container queries shed time/labels as lanes tighten — that's the whole density-adaptation story.
- **Density zoom = one abstract `DensityController`** (wheel/pinch/ease/persist mechanics) with per-view subclasses owning what zoom *means*: `DayDensityController` (`--_week-zoom` multiplier — the timed row is the pure CSS formula `zoom × (100% − header row − all-day row − gaps)`, day-fraction pinning measured once per gesture) and `MonthsDensityController` (`--months-zoom` multiplier, CSS-derived row height `(100% - header) / 12 * zoom`, ratio-scaled `scrollTop` pinning). **Zoom NEVER sizes tracks via measured px**: every `mitra-days` row is definite, because the row-spanning `mitra-day` subgrids give intrinsic rows unbounded growth limits — any free space (e.g. a grown window meeting a stale px row) pours into them and the subsequent remeasure reads its own bloat back, locking the layout (the historic resize bug). The base registers its listeners MANUALLY — `@a11d/lit`'s `@eventListener` keeps initializers in a set subclasses share with their base (broken copy-on-write), so a decorated subclass would leak listeners onto every sibling. Hosts whose scroll handler derives state from the scroll position must skip frames while `density.active` — per-frame pinning otherwise walks the navigating date (and its ±9-month fetch window) through every intermediate month; the controller re-dispatches one `scroll` on settle.
- **The strip owns its scroll position — the browser must not**: `overflow-anchor: none` on the host (native scroll anchoring fights the windowed rows swapping above the viewport and can runaway-feed the scroll→date handler), and when a scroll-driven `navigatingDate` set regenerates the buffer (`buffer.days` identity changed), re-anchor immediately via `scrollToDate` — every row just shifted under the unchanged scroll offset.
- **Gestures**: `EntryDragController` grid `'year'` — day-granular all-day create/move/resize like month (click quick-creates); every view (week/month/year) renders its cells as `mitra-day`, so the controller matches/snapshots them by that tag (each carries `data-date`, which the snapshot reads). The month rail navigates to the month's **middle** and fires `switchToMonth` — the month view centers the target's *week*, and day 1 often sits in a week still belonging to the previous month.
- **A new Light-DOM component's `static styles` MUST be registered in `Mitra.ts`'s aggregated styles** — light-DOM components (`createRenderRoot() { return this }`) get no automatic style adoption from lit; the app shell collects every component's styles into the one global sheet. Forgetting this renders the component completely unstyled with no error.

## View transitions

- **All of it lives in `frontend/calendarTransition.ts`** — `transitionCalendar(scope, type, update)` is the only entry point. Never call `startViewTransition` anywhere else.
- **Scoped, not document-wide**: `element.startViewTransition` (Chromium 147+) on the persistent `.calendar` wrapper in `PageCalendar` — the sidebar, header and dialogs sit OUTSIDE the scope, so nothing can paint over them and they stay live and clickable. Unsupported browsers switch instantly; **do not add a `document.startViewTransition` fallback** — it re-creates every glitch this replaced. The wrapper is `contain: layout; overflow: clip` and deliberately NOT a query container (Days.ts's `100cqi` math must keep resolving against `main`).
- **Navigation only.** View switches and source show/hide (the sidebar's `sourcesChange`). Background SSE refreshes apply in place with NO transition: the store adopts server values onto the same instances, so they repaint same-frame — animating them morphed the grid on every edit and snapped any running switch to its end frame (a second `startViewTransition` skips the first).
- **Entries are named just-in-time, viewport-bounded, capped** (40, nearest-to-center), pairs-only on the new side, cleared on `finished`; **at rest nothing carries a `view-transition-name`**. Cost is per named element and offscreen ones are still captured "as if scrolled to", so a permanent name on every segment captured the whole buffered range (~70 day columns, ~600 year-strip cells). Measured: a CSS-name-everything variant captured 688 elements and stalled ~1.4s on a fast machine vs 41 and ~100ms.
- **The grid's frame must be named too** — naming hoists an element OUT of its stacking context into the flat pseudo tree, which paints above the scope's snapshot, so any unnamed sticky chrome gets slid over by every entry. Each view marks its frame `data-chrome` (time axis, zone header, all-day corner, weekday rows, the year strip's month rail, and the week's column titles via `mitra-day[column-header]`); the helper names those `match-element` — browser-minted from element identity, so unique by construction (**a duplicate name aborts the whole transition**) and self-pairing. Frame only, NOT every date numeral: a chip crossing a numeral reads as movement, crossing the frame reads as broken — and that keeps the set bounded.
- Ship `::view-transition { pointer-events: none }` (the overlay otherwise eats clicks for the whole animation) and skip under `prefers-reduced-motion`.
- **Debugging**: `getAnimations()` filtered to `::view-transition-group` MISSES unpaired participants (they only get old/new fade animations) — dump the DOM pseudo-element tree instead; sibling order there IS paint order. Scoped transitions auto-nest participants under `::view-transition-group-children(root)`, so a name inside a named ancestor nests rather than double-drawing.

## Commands & keyboard shortcuts

- **One class per action, one registry, three views.** `frontend/commands/` holds the `Command` abstract class plus a class per user-invocable verb (grouped by domain: `entries.ts`, `views.ts`, `navigation.ts`, `app.ts`), each self-describing (palette `heading`/`icon`/`keywords`, the bare `keys` it answers to, its shortcut-sheet `group`) and self-executing. The `@command()` decorator registers the class (same pattern as `@integration`); **module-evaluation order in `commands/index.ts` IS display order**. The command palette, `PageCalendar`'s single keydown interceptor, and `DialogKeyboardShortcuts` all derive from this registry — adding a command class updates all three, so they cannot drift.
- **A command's facts are plain `readonly` FIELDS**, not getters. `t()` returns a lazily-stringified `LocalizedString`; it binds `Localizer.languages.current` at call time, but Mitra resolves the language once at boot (`?lang=` → localStorage → navigator — there is no in-app switcher), so a field translates exactly as correctly as a getter (verified in both `en` and `de`). Use a **getter** only for values depending on LIVE state — the current view (`NextPeriod.heading`) or the layout direction (`keyLabels`). If a language switcher ever lands, re-instantiate the registry on change rather than reverting every fact to a getter. The declaration forms are load-bearing: **every fact is `abstract readonly`**, which accepts a field OR a getter (a `declare`d field would reject the getter form — TS2611) and forces each command to state all of them explicitly, `undefined` included, so a palette-only verb says so out loud instead of by omission. Members carrying a **default** (`shortcutLabel`, `keyLabels`, `matches`) are real accessors, so overrides must also be accessors — under `useDefineForClassFields: false` a subclass field emits a constructor assignment that a getter-only base property throws on. Prefer DERIVING over overriding those: the arrow keys flip for RTL by computing `keys` alone, and the match, the palette hint and the sheet's chip all follow. Class/interface declaration merging is not an option (banned by eslint's `no-unsafe-declaration-merging`, and it would let a subclass silently omit a required fact).
- **Context is resolved, not passed**: commands reach the page through `Mitra.instance.calendar` (the framework's `queryInstanceElement`-resolved application, narrowed on `Mitra`) at execution time — no constructor wiring, and a command can drill into as much page state as it needs. **Both are non-nullable**: the `@application()` decorator appends the instance at module evaluation, and a command is only reachable from surfaces the page itself owns, so neither can be absent when one runs — nothing may touch `calendar` during construction though, since the registry is instantiated in the page's own field initializer. Members a command drives must be public on `PageCalendar` (`setView`, `navigatingDate`, `navigationStep`, `goToDate`, `toggleSidebar`).
- **Every surface runs a command through `Command.dispatch()`**, never `execute()` directly: it absorbs the one rejection that isn't a failure — `DialogComponent.confirm()` **rejects with `DialogCancelledError`** when the user dismisses a dialog, so a dialog-opening command otherwise leaves an unhandled rejection on every Escape (a long-standing wart the central dispatch finally fixes). Genuine failures still reach the console.
- **Deliberately NOT command classes**: pointer gestures (`Ctrl`+drag scope bypass, `Alt`+click task status, `Ctrl`+scroll zoom) and keys needing their owner's state or guards (`Ctrl+P` — must work inside text fields; `Delete`/`Ctrl+Delete` — gated on the open entry editor; `/` — the page's search affordance, pointless inside the palette it opens). These stay with their owners and appear in `DialogKeyboardShortcuts` as hand-written vocabulary rows only — they are not palette-listable commands, so forcing them into the registry would be semantically wrong.
- **`mitra-command-palette` is a pure view.** The page passes its once-instantiated command list in as a property; the palette only filters (`commandMatches`: every query term must appear in heading+keywords), navigates (arrows/Enter, hover) and dispatches. Picking an entry emits `navigate` with its start **and** calls `EntryStore.requestOpen(id)` so its editor pops open once its segment renders; picking a command runs `execute()` after closing.
- **Opening a picked entry reuses the draft auto-open mechanism, generalized.** `EntryStore.requestOpen(id)` sets a pending `openEntryId` (sibling to the draft's `autoOpen` flag); `EventSegment.updated` opens the run-start segment (`!hasPrevious`, so a multi-day entry opens once) when `shouldOpen(entry)` matches, then `consumeOpen()`s it. The id is kept until consumed so it survives the async refetch the navigation triggers (cross-month picks work), and `shouldOpen` matches `entry.recurrenceMasterId === openEntryId` too, so picking a recurring master opens whichever occurrence the navigation lands on.
- **Entry search is backend-side and unwindowed** (`GET /entries/search?q=`): LIKE over heading/description/location across visible sources (limit 20, newest first), because the calendar only ever fetches ±1 month — the palette must find *everything*. Recurring masters match as themselves (one row stands in for its series). Debounced 200ms with a monotonic token so only the latest response lands.
- **Open affordances — three keys, all equal, but only ONE is advertised:** a bare `/` (owned by the page, since opening the palette from inside the palette is meaningless) plus Ctrl/Cmd+**P** *or* **K** (one window keydown listener owned by the palette itself, `CommandPalette.hotkeys`), and the header's fake search box. `CommandPalette.hotkey` is `'/'` — what the **prominent** UI teaches, because it's one key with no chord and no per-platform spelling. That is a presentation choice, NOT a tiering: both chords are listed in the shortcut sheet and in `docs/guides/keyboard-shortcuts.md`, since a shortcut nobody can discover may as well not exist. Don't "simplify" the sheet by dropping them — a `button.search` styled like an input, centered between flex spacers, collapsing to an icon-only button under `@container (max-width: 40rem)` (the header is an inline-size container).
- **It's a native `<dialog>` with `closedby="any"`** for light dismiss — no hand-rolled backdrop-click handler (that pattern closes on the *trigger's* double-click). Styling follows the popover look: translucent `color-mix` surface + `backdrop-filter: blur`, `@starting-style` entry animation.
- **"Create Entry" reuses the gesture-draft flow** (`EntryStore.upsertDraft` + `openDraft`): a blank one-hour draft at the next full hour today on `getPrimarySource()` (Api.ts — default-or-first-visible; also what the drag controller uses). It always `setView('week')`s first: the week's timed grid renders every draft, whereas a crowded month cell folds it into "+N more" and the auto-open editor would never appear.
- **The keyboard interceptor** (`PageCalendar.handleKeyDown`, one window keydown listener matching the registry) MUST stand down for any editable target — `<input>`, `<textarea>`, `<select>`, AND `contenteditable` (the sidebar's inline source-rename is a contenteditable div, so typing "m" once switched to Month mid-rename), plus Ctrl/Cmd/Alt chords, `e.isComposing` (IME), and **any open modal dialog** (everything behind it is inert, so `e.composedPath()` containing an `HTMLDialogElement` is the test). A `Command`'s `keys` are bare keys for exactly this reason; a key that can't live behind these guards belongs to its owner, not the registry.

## Sources & entry types (type-agnostic sources)

- **A source is NOT a type — it DECLARES which types it can hold.** `Source.entryTypes` replaced the old `Source.type`/`SourceType` split, and the type of a given entry lives where it always was persisted: `Entry.type`. So **one CalDAV collection is ONE source row**, not an event/task sibling pair. The list is discovered per source, never hardcoded per provider — CalDAV reads `supported-calendar-component-set` (a VEVENT-only work calendar must not offer tasks; per RFC 4791 §5.2.3 an absent/empty set means "everything", so it yields both), Notion is always `[Task]`, Dev is per seeded source (its `Personal` sample deliberately holds BOTH, so the editor's type switch is reachable in development). A collection accepting neither `VEVENT` nor `VTODO` is dropped at discovery. Behaviour lives on the entity: `Source.supports(type)` (an empty list reads as "everything") and `Source.defaultEntryType` ("an event wherever it can hold one, else its own type"), which the create gestures, the palette's Create Entry, `Entry.migrateTo` and the POST route all defer to. What a source accepts is provider truth, so `Integration.getSources` simply refreshes it each reconcile (unlike `name`, which is user-owned — see `remoteName`).
- **`EntryType` is a VALUE OBJECT, not an enum** (`shared/EntryType.ts`): private constructor, one static instance per type (`EntryType.Event`/`.Task`, plus `EntryType.all`), so `===` is the whole comparison story and the type can carry behaviour (`isTask`/`isEvent`, which the views and the CalDAV writer read instead of re-deriving from a string). It still *looks* like a string wherever it must: `toString`/`toJSON` yield the `EntryTypeValue` (`'event'`/`'task'`), so an API response says `"type": "task"` and a template interpolates the same word as before. `TaskStatus` is deliberately still a plain enum — the same recipe applies if it ever needs behaviour.
- **A value object on an entity costs THREE things, and all three are load-bearing.** Learned by breaking each one:
  1. **A MikroORM custom `Type` per column** (`EntryTypeMapper` → `text`, `EntryTypesMapper` → `json`; `Type` is re-exported from `shared/orm.ts` like every other ORM import). The columns are unchanged from the enum era — `entry.type` is still `'task'`, `source.entry_types` is `["event","task"]` — so nothing about the schema encodes the class.
  2. **A private backing field plus an accessor pair** (`Entry._type` ↔ `type`, `Source._entryTypes` ↔ `entryTypes`, both with `fieldName` pinning the column). The SETTER is what carries the object across the API: `@a11d/api`'s reviver `safeAssign`s the raw `"task"` off the JSON onto the property (it honours setters — `Object.isWritable` checks `descriptor.set`), and the setter runs it through `EntryType.parse`. Without it the frontend holds strings while the backend holds instances, and every `===` silently fails.
  3. **An explicit `toJSON`** on each entity, because `@model`'s serialization is `{...this}` — a spread copies the own `_type` FIELD and never the prototype accessor. Each re-exposes the accessor under its wire name **as the plain value**, which serves both directions: the backend's responses stringify through it, and the client's request bodies are built from it (`Api.createEvent`/`updateEvent` send `entry.toJSON()`, not a spread) — and `Api.handleRequest` **structure-clones** a body, which would flatten a class instance to `{value:'task'}`. A string survives that; an object does not.
- **Assigning `Entry.type` IS the conversion** (there is no `setType`): the setter clears `status` unless the new type is a task, so the editor's draft switch and `migrateTo` both just assign. It accepts `EntryType | EntryTypeValue`, which is also the parse seam above. An unmodelled value throws — the POST route therefore uses `EntryType.tryParse` to answer 400 rather than 500.
- **`Source.keyOf` is the collection URL ALONE** (the `type#` prefix is gone) — the identity `applyAndSync` matches plain incoming DTOs against managed rows with; the static-not-getter rule for structure-cloned bodies is unchanged.
- **Why the split had to go**: two sources watching one collection URL was the sole reason for two `syncCollection` passes + two sync tokens per collection, `siblingSourceIds` + the cross-source duplicate guard, the per-source component filter, and the "write the matching component so the sibling doesn't re-ingest it" rule — all deleted. It also didn't scale: every future component type (VAVAILABILITY, VJOURNAL…) would have added a third and fourth row per collection. The per-type knobs it bought (separate colour/hidden/order per type of one collection) went unused in practice.
- **CalDAV sync is ONE pass that ingests every modelled type**: `syncSourceEntries` reads `vevent` AND `vtodo` subcomponents of each changed resource and sets `entry.type` from the component that produced the row (`component.name`); RFC 4791 §4.1 forbids mixing component types within one resource, so a resource's rows stay single-type and the `(sourceId, uri, recurrenceId)` unique index is unaffected. Writes are unchanged: `entry.type.isTask` still decides VTODO/`DUE`/`STATUS` vs VEVENT/`DTEND`.
- **Creation answers "what type?" without a source split.** Gestures and the palette default to `source.defaultEntryType` (an event unless the target is tasks-only), and a **draft** on a source holding both gets an event ⇄ task `<select>` row in the editor (`EventDetails.entryTypeTemplate`, sharing the source row's shape via `&:is(.source, .entry-type)`). **Draft-only, deliberately**: converting a *persisted* entry on CalDAV means deleting and re-creating the resource (RFC 4791 §4.1), a write path with its own failure modes — and, mechanically, `editEquals` counts `type`, so a switch on a saved entry whose PUT ignores `type` would leave it permanently dirty in a commit loop. The POST route rejects a type the target can't hold (loud, per the Notion-recurrence philosophy).
- **NO migration was written, by explicit decision** (same precedent as the OIDC and all-day-canonicalisation changes): a pre-change database keeps its old event/task row pair, and the fix is a user action — delete the integration and add it again. Documented in `docs/integrations/caldav.md`'s troubleshooting. But **"breaking data" must never mean "breaking the boot"**: `orm.schema.update()` rebuilds the table, and a NOT NULL column with no default fails that ALTER outright on any existing database — the server then never starts, so the user can't even reach the UI to re-add. `Source.entryTypes` is therefore **nullable**, read through a normalizing getter (`?? []`, i.e. "the provider never said"), and the next reconcile fills it in. Verified by booting the pre-change build against a scratch database and then the new build against that same file — worth repeating for any future column.
- **A type FORMATS ITSELF**: `EntryType.format()` ("Event") and `formatPlural()` ("Events") — the editor's switch and the integration checklist's subtitle ("Events · Tasks") both read them, so the vocabulary can't drift into a labels module. They are **frontend-only by contract**, since `t()` is a frontend global: never call them from backend code (the same rule the provider `description` statics follow). `scripts/i18n.ts` therefore scans `src/shared` for translation calls as well as those statics — and mind that its regex reads DOC COMMENTS too, so never spell the literal call form in shared prose (it lands in the key list).
- **A global "show/hide tasks" lens is FUTURE direction, not built** (it was written once and removed): a source holding both types means hiding tasks can no longer be expressed by hiding a row, so the eventual answer is one rendering filter — but the shape it should take (and whether virtual sources subsume it) is unsettled, so nothing ships until it is.

## Sidebar & the source icon

- **`<mitra-source-icon>` (`components/SourceIcon.ts`) is the ONE way a source is ever drawn**: what it can HOLD, in the source's own colour, `.source` in, nothing else. Three glyphs, one per answer — `calendar` for events only, `list-todo` for tasks only, `calendar-check` for a collection that takes BOTH (the common CalDAV case, and the only row where the editor offers a draft's type switch). The sidebar marker's tooltip is therefore the default-source hint alone (the old "Tasks — …/Events — …" prefix went with the split). Used by the sidebar's rows, the entry popover's source row *and* its `<option>`s, and the integration dialog's checklist. There is deliberately **no separate colour chip beside it** — the old chip+glyph pairing made two icons compete for one rail, pushed every label deep to the right, and, because each site paired them its own way, had already drifted into two different-looking versions of the same idea. Never hand-roll a source’s colour square or type glyph again; extend the icon. `selected` (solid fill + `colorContrast()`-flipped glyph) means standing FOR the source — only the sidebar's default-for-new-entries passes it; a picker's current option is already marked chosen by the picker.
- **`<selectedcontent>` cannot render the icon.** A customizable `<select>` draws its chosen option by CLONING that option's DOM, and the clone (a) carries no JS properties and (b) is taken *before* the icon's first lit update, so even reflected attributes aren't there yet — it comes out a colourless `calendar`. So the entry popover's source row renders **its own** icon into the grid's leading column (`pointer-events: none` so clicks still reach the select; both on `grid-row: 1`, or auto-placement drops them onto separate lines) and hides the cloned one with `selectedcontent mitra-source-icon { display: none }`. Same constraint applies to anything else put inside an `<option>`.
- **The sidebar's alignment is ONE grid, not a set of matching paddings.** `.integrations` declares `grid-template-columns: 0 auto 1fr auto 0` (marker | name | actions between two **zero-width edge tracks**) and `.integration`, `.integration > header`, `.sources` and `.source` all re-expose it with `grid-template-columns: subgrid` + `grid-column: 1 / -1`, so a heading's ⋯ and a row's ⋯ share a track by construction. Three subgrid facts this rests on: **padding on a subgrid item shifts its tracks off the parent's** (hence the edge tracks carry the row inset — padding cannot); **`position: sticky` on a grid item is clamped to its own grid area**, i.e. it does not stick (sticky account headings and structural alignment are mutually exclusive — structural won); and **`all: unset` resets `grid-column`**, so it must come first in any rule that also places the item. A mark also needs `justify-self: start` wherever it shares a column with something wider (the popover gutter is as wide as a toggle switch).
- **The default source is `getPrimarySource()`, never `getDefaultSourceId()`.** The stored preference is only a hint: creates resolve to "the stored default *if it is still visible*, else the first visible source". Reading the stored id in a view leaves the marker unlit when nothing is stored and lit on a hidden row that creates no longer target. The marker's click therefore has three states: set / clear / **stand down** (one holding the default by fallback has nothing to unset).
- **A scroll container whose content must stay aligned with pinned siblings needs a reserved gutter.** A classic scrollbar eats the CONTENT box, so before `scrollbar-gutter: stable` the sidebar's whole list jumped inward by the thumb's width the moment one more source made it overflow — and sat that far short of the footer meanwhile. The lane is sized explicitly via `::-webkit-scrollbar`, because any non-`auto` `scrollbar-width` makes Chromium **ignore every `::-webkit-scrollbar-*` rule** (that's what produced Windows stepper arrows), and because the padding beside it has to be its exact complement.
- **Manual sidebar order is a nullable `order` column** (`Source.order` within an integration, `Integration.order` among accounts; since folded into the initial migration). Display order is ONE comparator — `shared/order.ts byOrder` (`order` ascending, nulls last) — applied by the CLIENT at the `fetchIntegrations` boundary as a **stable sort over the server's un-ordered response**; the GET deliberately has NO SQL `orderBy`, because `order asc nulls last` leaves SQLite's tie order arbitrary and could reshuffle every pre-feature (all-null) sidebar, whereas the stable sort provably keeps the never-ordered rest exactly what it always was (in practice: discovery/insertion order for sources within an account via the FK index; the `(userId, uri)` unique index's order for integrations). So a never-ordered list keeps today's discovery/connection order and a newly discovered, newly enabled or re-appearing source APPENDS instead of reshuffling a hand-ordered list. Writes are **wholesale, never incremental swaps** (`PUT /sources/order` — one integration's visible rows — and `PUT /integrations/order`, both `{ ids }` through `shared/order.ts applyOrder`): listed rows take their index, every unlisted sibling drops back to null, which is what keeps stale numbers on rows that left the visible list from interleaving later. The client (`Api.reorderSources`/`reorderIntegrations`) re-sorts its local store with the same `applyOrder` + `byOrder` before the request — no refetch, like rename/recolour. The gesture is **@3mo/reorderability** (extracted from this feature into its own package; see its docs/stories): items declare themselves via the `item({ index, disabled?, handle?, dragImage? })` element-part directive inline in the template — NO identity data attributes in the DOM — and the drop reports `(source, destination)` as indices among THAT controller's items. **Grouping is ONE CONTROLLER PER LIST** (`integrationsReorder` for the accounts, one per account in `sourcesReorder` for its sources): a controller only sees its own registered items, so a drag can never carry a row into another account, and the union-of-slots clamp enforces it geometrically. The `handle` is what disambiguates the two nesting levels — a `.source` sits inside a `.integration`, so the accounts controller grabs only from the heading's `.title` and stands down for a row (and for the heading's ⋯). Per-account controllers are created lazily during render, which is safe only because the package registers itself as its own event listener (a bound-handler field would miss `hostConnected`, since lit calls it inside `Controller`'s `super()` before field initializers run — the drag then dies silently); `removeController` prunes an account's controller when it is disconnected. Everything Mitra-specific stays in `Sidebar.commitOrder`: it splices the id list and writes it wholesale, so the DRAG and the ⋯ menu's Move up/down share one commit path. Styling contract: `[data-reordering]` on the sidebar host while a drag is in flight, `[data-reorderability=dragging|drop-before|drop-after]` on each item. The ⋯ menus carry Move up/Move down as the accessible fallback. Reordering deliberately feeds `getPrimarySource()`'s fallback: dragging a source to the top IS how you pick the default-for-new-entries when none is stored (the marker's hint already says "as the first one shown"). Sources reorder only WITHIN their integration — cross-integration placement is a future grouping feature, not a drag away.
- **The eye is the LAST action in a source row, ahead of convention.** It's the one that stays on show for a hidden source, and only in the final slot does it sit on the trailing edge instead of floating in the gap the (invisible) ⋯ would have filled. Its menu anchors to the whole `.actions` group, not to its own trigger, so it opens clear of the eye beside it.

## Recurrence (RFC 5545)

- **One master row, occurrences expanded on read — never stored.** A recurring series is a single `Entry` carrying `rrule` (+ `uid`); `CalDAV.expandRecurrence(raw, windowStart, windowEnd)` iterates the rule into the occurrences intersecting the visible window. `GET /entries` **excludes masters** (`rrule != null`) from the plain rows and emits synthetic per-occurrence `Entry` objects instead, so the bare master (whose `DTSTART` is only its first instance) is never rendered on its own. Occurrences are non-persisted, with a **CSS-ident-safe id** `` `${master.id}__${epochMs}` `` (underscores + digits — colons/dots break `anchor-name`/`view-transition-name`) and `recurrenceMasterId` set.
- **Overrides & exclusions.** A single edited occurrence syncs from CalDAV as its own row with a `RECURRENCE-ID`, linked to its master by shared `uid` (a post-loop pass in `syncSourceEntries`, scoped to the source); the GET skips expanded dates that already have an override row. `EXDATE`s are applied during expansion (matched by epoch-ms).
- **One resource, MANY rows.** A compliant server (Google, iCloud) bundles a series master and ALL its override components into ONE `.ics` resource (RFC 4791: one UID per resource) — never assume one component per resource. `syncSourceEntries` therefore upserts one row per `vevent`/`vtodo` component; within a resource a row's identity is its `RECURRENCE-ID` (the master has none) — the unique index is `(source_id, uri, recurrence_id)`, NOT `(source_id, uri)`. Consequences for the write paths: select the row's component via `CalDAV.componentFor` (never `getFirstSubcomponent` — that edits whichever component happens to be first); after any resource write, `syncResourceRows` mirrors the new `raw`/`etag` onto the resource's other rows (each keeps a copy — a stale sibling etag would 412); `excludeOccurrence` also strips a bundled override component of that instant (EXDATE alone only prunes the recurrence SET — the override would keep the instance alive) and its local row; `deleteEntry` on an override row routes through the master's exclusion — deleting the shared resource would kill the whole series. An override that vanishes from the resource (occurrence reverted) loses its row on the next ingest. Rows synced BEFORE a parsing improvement don't self-heal (unchanged resources aren't re-listed by sync-token deltas) — "Re-import entries" is the recovery path.
- **Editing is series-wide (current version).** There is no per-occurrence editing yet. Editing a rendered occurrence routes to the master via `recurrenceMasterId` (`Api.updateEvent` sends only series-wide fields, so the master keeps its own `start`/`end`); deleting removes the whole series. **`Entry.partOfSeries`** (`!!rrule || isRecurring`) is the intrinsic test for "belongs to a series" — its schedule (date/time/all-day) is read-only and it isn't drag/resize-movable; only the Repeat field stays editable. Setting a repeat on a non-recurring entry makes it a master (its own id; the schedule then locks — remove the repeat to edit times again).
- **RRULE strings are authored on the frontend.** `src/frontend/recurrence.ts` owns the whole RRULE subset: `buildRRule`/`parseRRule`, the date-derived quick presets (`recurrencePresets`), structural equality/match, and the human `recurrenceLabel`. `mitra-repeat-field` (the Notion-style trigger + preset dropdown + Custom dialog) mutates `entry.rrule` in place and fires a distinct `recurrenceChange`. The **backend never builds rules** — it just writes the string onto the master's `.ics`: `CalDAV.createEntry`/`updateEntry` set it via `ICAL.Recur.fromString(rrule)` and drop it (collapsing the series) via `removeAllProperties('rrule'|'exdate')`. The routes validate it first (`CalDAV.isValidRRule`, 400 on junk) so a bad rule can't 500 the `.ics` writer.
- **Recurrence edits go through a dedicated path, never the content-edit path.** `Api.updateEvent` (heading/description/colour/status, plus the move-to-master routing for occurrences) **never writes `rrule`**; only `Api.setRecurrence` does (string = set, `null` = remove; `entries.ts` PUT maps absent = keep). This split is load-bearing: a synced *override* (an externally edited single occurrence — `recurrenceMasterId` set, but no `rrule` of its own) renders as an editable row, and inferring `rrule` from it on a benign rename would otherwise wipe the master's whole series. So content edits must stay rule-silent.
- **Expansion works without an `.ics` too.** `expandRecurrence(raw,…)` (CalDAV, carries EXDATEs/anchor from the stored `.ics`) and `expandRecurrenceFields(rrule, start, end, …)` (column-only, for integrations like `Dev` that persist no `.ics`) share one `iterateOccurrences` core; `entries.ts` picks the column path when `master.data.raw` is absent. **ical.js 2.x has no `Recur.between()`** — the core iterates `rrule.iterator(anchor)` and stops once occurrences ascend past the window, with a generous iteration cap (a far-future window must still be *reachable* for a dense daily series) and a no-advance guard against a malformed rule.
- **Backfill:** entries synced before recurrence support have the `RRULE`/`RECURRENCE-ID` in `data.raw` but NULL columns, and the etag-skip won't re-read them — `backend/orm.ts` parses the candidates once on boot and links overrides to masters by UID (idempotent).

## Participants (RFC 5545 ATTENDEE / ORGANIZER, iTIP RFC 5546, CalDAV scheduling RFC 6638)

- **Scope: mitra says WHO is invited, the provider does the notifying.** Writing ATTENDEE/ORGANIZER onto the resource is the whole contract — a scheduling server (RFC 6638: Google, iCloud, Nextcloud, Fastmail…) is the scheduling agent for every attendee we write and mails the invitations and cancellations itself, and it is also what parses inbound replies into PARTSTAT, which we then read back on sync. So **nothing here sends, suppresses or receives mail**, and no write stamps `SCHEDULE-AGENT`. Servers that only STORE attendees notify nobody, and that gap is deliberate and known: closing it (client-side iMIP over SMTP, plus an inbound channel for replies) is a separate feature on its own branch, not something to reintroduce here piecemeal.
- **One JSON column, one domain collection.** `Entry.participants` (`shared/Participant.ts`) is the invitee list — `Participant` value records, `null` for "none", the same tri-state wire convention as `reminders` (array sets, `null` clears, absent keeps) and the same **replace-don't-mutate** rule (clones share the array, so a new one is always assigned). The ORGANIZER is *in* the list (`organizer: true`); `self` marks the account's own address, stamped at sync/seed time. Behavior is object-oriented, not free functions: **`Participants`** (an `Array` subclass, so the column/wire/`Object[equals]` all see a plain array — statics must dodge `Array.from`/`of` names, and `Symbol.species` is pinned to `Array` so projections stay plain) owns the whole list domain — `Participants.normalize` is the single canonical shape (lowercase e-mails, *explicit* role/status defaults, dedupe by e-mail, ≤ 1 organizer; idempotent), the reads (`summary`, `emails`, `mailto`, `counts`, `organizer`, `self`, `others`, `organizerFirst`, `manageable`, `initialOf`) and the list operations (`inviting`, `marked`). Hydrated/wire arrays are plain, so behavior re-enters the domain via `Entry.participantList`; the **`Entry` aggregate methods are thin delegations** (`invite`, `markAllParticipants`, `clearParticipants`) the editor wires straight to, like the timing methods.
- **`participants` is a provider capability** (see `Integration.capabilities`): Notion turns it off — a page has no invitees, and its people property is workspace membership, not RFC 5545 group-scheduling. The editor hides the field; the routes reject participant-carrying writes to a non-supporting provider with a loud 400 (the Notion-recurrence philosophy — never silently drop a list), which also covers *migrating* a group-scheduled entry there.
- **Permissions are iTIP, enforced in the backend.** Only the organizer may change the list: `Entry.canManageParticipants` (no organizer = the user's own entry = manageable; else `organizer.self`). The PUT route 403s a list *change* on a foreign-organized entry — content edits that echo the stored list back unchanged pass — and the UI disables the batch actions (mark all required/optional, remove all) plus hides the add-input, with a title explaining why.
- **"Who am I" = `Integration.addresses`.** CalDAV discovers it once per account from the principal's `calendar-user-address-set` via tsdav's `fetchCalendarUserAddresses` — call it with `{}`: tsdav injects its own discovered account, and passing one *replaces* it. Falls back to an e-mail-shaped username; `merge` clears the addresses when the username changes; the Dev sample seeds `me@example.com`.
- **CalDAV mapping** lives in the pure statics `CalDAV.participantsFrom`/`writeParticipants` (unit-tested like the URL helpers): CN↔`name`, ROLE↔`role`, PARTSTAT↔`status`, the organizer merged with its own ATTENDEE row (its actual reply wins), CUTYPE `ROOM`/`RESOURCE` skipped, `RSVP=TRUE` while a reply is pending. On change the ATTENDEEs are rewritten wholesale; ORGANIZER is only ever *added* (the entry became group-scheduled — the frontend enlists the account as organizer on the first invite) or *removed* (list cleared) — never rewritten to someone else.
- **UI:** `mitra-participants-field` in the details popover — a header (count, "2 yes, 1 no, 2 awaiting" summary, a mailto "Email participants" and the batch menu incl. "Copy participants' emails") over the participant rows: initial-avatars tinted by the deterministic `Color.get(email)`, reply badges (green ✓ / red ✕ / grey ?), **selectable e-mails and deliberately no per-participant actions**; > 5 rows collapse behind "See all N participants". The component only renders and forwards to the domain (`Entry`/`Participants` above), which is where the logic is tested. Its row is a `.field` like every other (see `field.css.ts`), so it carries **no anchor token of its own** — the batch menu resolves the field's scoped `--field`. That also means the menu must be a DIRECT child of the component: nested one level deeper, the placement rule (`> menu[popover]`) silently misses and the generic below-the-anchor default wins, which under a field anchor drops it below the whole block.

## Build / test / run

- **Node 25+** is required at build & runtime (Temporal API behaviour) — pinned in the Dockerfile and CI.
- **Typecheck (one-shot):** run `tsgo` (`node_modules/@typescript/native-preview-<platform>/lib/tsgo[.exe] --noEmit`). esbuild does NOT typecheck.
- **Lint:** `npm run lint` → `eslint .` (flat config `eslint.config.mjs` extending `@a11d/eslint-config`). Pinned to ESLint 9 (`eslint-plugin-lit@1` breaks on ESLint 10). Style is enforced: tabs, single quotes, **no semicolons**, **no trailing newline** (`eol-last: never`), `no-console` allows only `warn`/`error` (off in `scripts/**`), `^_`-prefixed args are ignored. Run `eslint . --fix` after edits.
- **Tests:** `npm test` → `scripts/test.ts` esbuild-bundles `src/**/*.test.ts` → `out_test/`, then `node --test`. Use the Node built-in runner (`node:test` + `node:assert/strict`) with real `DateTime`.
- **Dev:** `npm start` → `scripts/dev.ts`: `tsgo --watch` + esbuild watch for backend (`out/server/server.mjs`, run via `node --watch`) and frontend (`dist/`).
- **Production build:** `npm run build` → `scripts/build.ts` (one-shot, no watch): backend bundle + minified frontend → `dist/`. The esbuild config (entry points, externals `better-sqlite3`/`tsdav`, the `createRequire` banner, the `index.html` shell) is shared between dev and prod in `scripts/esbuild.ts` — change it there, not in two places. `data/` must exist before boot (better-sqlite3 won't create it); a committed `data/.gitignore` keeps the dir, and the Dockerfile `mkdir`s it.
- **Dev sample data:** `src/backend/Dev.ts` `seedDev(orm)` **persists** a real `Dev` sample integration + sources + entries (idempotent, keyed by a stable id; never deletes), gated by `process.env.MITRA_DEV` (set only by `scripts/dev.ts`). It seeds real rows — *not* a read-only overlay — so hiding sources, editing, creating and deleting all work through the normal routes. The user can simply delete the integration when done. Seeding runs once; a `npm start` restart re-checks but won't duplicate.

## Docker, CI & releases

- **Image:** multi-stage `Dockerfile` (build → `npm prune --omit=dev` → `node:25-bookworm-slim` runtime). Both stages share the base so the prebuilt/compiled `better-sqlite3` binary is ABI-compatible (the builder has `python3`/`make`/`g++` so it compiles if no prebuild exists for the Node 25 ABI). The `org.opencontainers.image.source` LABEL links the image to the repo on GHCR. Published to `ghcr.io/a11delavar/mitra`.
- **Tagging is `docker/metadata-action`, not hand-rolled** (`.github/workflows/docker.yml`): push to `main` → `dev` + `sha-<short>`; **push tag `vX.Y.Z`** → `X.Y.Z`/`X.Y`/`X`/`latest`; pre-release tag `vX.Y.Z-rc.N` (channels `rc`/`beta`/`alpha`) → only the precise tag (`flavor: latest=auto` auto-skips floating tags + `latest` for pre-releases); PRs build-only. Multi-arch amd64/arm64 via QEMU+buildx. Image tags come off the **git ref**, so they don't depend on a GitHub Release existing.
- **Changelog lives in the repo** as `CHANGELOG.md`, generated from commits by **git-cliff** (`npm run changelog`, config `cliff.toml`) and then hand/AI-editable. Release flow: `npm run changelog -- --tag vX.Y.Z` → edit the new section → `commit -m "release: vX.Y.Z"` → `git tag vX.Y.Z && git push origin main vX.Y.Z`. **Order matters:** the changelog edit must be committed *before* the tag points at it (the release body is extracted from the file at the tagged commit).
- **Releasing = pushing the SemVer tag.** That one push fans out (in parallel) to `docker.yml` (builds images off the git ref) and `release.yml` (publishes the top section of `CHANGELOG.md` as the GitHub Release body; pre-release if the tag has `-rc`/`-beta`/`-alpha`). Tag-driven on purpose — avoids the `GITHUB_TOKEN`-created-release-doesn't-trigger-workflows gotcha. The README "Releasing & versioning" section is the user-facing source of truth.
- **GHCR has no GC** → `.github/workflows/cleanup.yml` prunes untagged manifests + old `sha-*` tags (keeps `latest`/`dev`/releases). Ships in `dry-run` — verify before enabling.
- **Quality Assurance** (`.github/workflows/qa.yml`): three **parallel** jobs — type-check (`tsgo`), lint (`eslint`), test (`npm test`) — on push/PR. Publishing untested images is not acceptable.

## Conventions

- **Commits:** single-line `type: Capitalized phrase`. The type is load-bearing — `CHANGELOG.md` is generated from commit subjects (git-cliff, `cliff.toml`), so it decides the changelog section: `feat:`→Features, `fix:`→Bug Fixes, `perf:`→Performance, `refactor:`→Refactors, `docs:`→Documentation, `test:`→Tests, **`ci:`/`build:`/`infra:`→Infrastructure**, `chore:`→Chores, anything else→Other. `release:` commits are excluded. Commit ONLY when explicitly asked.
- **The commit subject IS the release note** — it lands verbatim in `CHANGELOG.md`, so write it for end users, not for the diff: state the visible change or benefit in plain language and avoid implementation detail (component/file names, and internal mechanics/jargon like *popover*, *pointer capture*, *light-dismiss*). Prefer the effect the user sees ("Keep the entry editor opening reliably when clicking an entry") over the cause ("Defer showPopover past the captured-pointer click"). `refactor:`/`chore:`/`ci:` subjects are the exception — they have no user-facing effect, so describe the internal change plainly.
- Indent with **tabs**.
- **License:** the project is **AGPL-3.0-only** (`LICENSE`, `package.json`, image label). Keep new workspace manifests consistent.
- Public repo: keep secrets/credentials and personal identifiers out of committed files; leave the git author config unchanged.
- **No real-world people references** in code, tests or seeds — no names or initials of actual people, even on `example.com`. Placeholder addresses derive from the *role* in the scenario (`organizer@example.com`, `optional@example.com`, `me@example.com`).
- **Domain-driven, object-oriented design:** behavior belongs on the domain — aggregate methods (`Entry.moveStart`, `Entry.invite`), value objects (`Recurrence`), or first-class collections (`Participants`) — not on context-less helper functions in loose modules.
